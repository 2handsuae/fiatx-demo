## 0. 一句话定位

Sumsub（KYC/KYT/Travel Rule/制裁筛查/持续监控）的 webhook → 翻译成内部领域事件 → 路由到各消费方。**平台侧只做翻译层 + 审计**，不重建合规执行管道。本文管：webhook 接入、ingest 去重、dispatch 路由、retry/dead-letter、模拟端点。**不**管：各消费方收到事件后怎么处置（去 v2/v4/v5/v6）。

## 1. 状态机（SumsubWebhookEvent）

- `PENDING → (dispatch 成功) DISPATCHED / (失败) FAILED → (retry 3 次仍失败) DEAD`
- 锚点：prisma `SumsubWebhookEvent`（eventNo/status/rawPayload/retryCount）

## 2. 数据模型要点

- **SumsubWebhookEvent**：每 webhook 一行；`dedupeKey` 去重（真实 webhook）；`rawPayload` JSON 存原始报文；`status`/`retryCount`/`lastError`
- **事件类型两类**：真实（applicantReviewed / applicantActionReviewed / applicantWorkflowCompleted / ongoingDocExpired）+ 模拟（**仅剩 `caseDecisionSimulated`**，V2 客户风险评估用）——均走同一 ingest→dispatch 管道。~~kytCheckSimulated / travelRuleCheckSimulated（充值老 mock）~~ 随 2026-07-31 充值单笔提交改造退役、~~withdrawKytCheckSimulated / withdrawTravelRuleCheckSimulated（提现老 mock）~~ 随 2026-08-04 提现真实 Sumsub 引擎（Task 5）退役——四者均已从 `dispatch()` 删除，全仓 grep 零命中，2026-08-07 复核订正（此前本文误留为仍存在的模拟类型）
- 锚点：prisma `SumsubWebhookEvent`

## 3. 关键流程（`sumsub-ingestion.service.ts` + controller）

- **接入**：`POST /webhooks/sumsub` → `handleWebhook()` 签名验证（`sumsubClient.verifyWebhookSignature`，失败抛 401）
- **ingest**：`ingest()` → 去重（dedupeKey）→ `createEventRecord()` 建 SumsubWebhookEvent(PENDING) → 触发 dispatch
- **dispatch 前置分流（充值交易 webhook，2026-07 落地；2026-07-31 由前缀匹配改为显式集合匹配）**：`dispatch()` 在按 eventType 的老 if/else 分支**之前**新插一段——`payload.type` 命中 **`KYT_VERDICT_TYPES`**（`deposit-sumsub/kyt-webhook-types.ts`，六项：`applicantKytTxnApproved` / `applicantKytTxnRejected` / `applicantKytTxnAwaitingUser` / **`applicantKytOnHold`** / `applicantKytTxnReviewed` / `applicantKytTxnCreated`）即整段转交 `DepositWebhookRouter.route()`（新模块 `deposit-sumsub/`），复用本表既有的去重/retry/dead-letter，只是路由目标从老 if/else 换成这个 router。
  ⚠️ **`applicantKytOnHold` 没有 `Txn`** —— 这是 Sumsub 官方的命名不一致（其文档自己也注明）。~~此前用 `startsWith('applicantKytTxn')` 前缀匹配~~，真实 on-hold 事件不以该前缀开头，**在最外层分流处就被丢弃**，挂起复核整条路失效；因我方 fixture 与全链路五处一致地写成 `applicantKytTxnOnHold`，演示与单测全绿、完全掩盖了缺陷（2026-07-31 修）。
  **修法约束（勿改回）**：不可放宽成 `startsWith('applicantKyt')` —— 那会把 `applicantKytAml*` 等同前缀的其它 KYT 族事件误吞进 deposit 路由。类型清单以 `kyt-webhook-types.ts` 为**单一真相源**，ingestion 前置分流 / `DepositWebhookRouter` / `DepositKytVerdictHandler` 三处共用同一份，不得各自维护副本。`DepositWebhookRouter` 再按 type 二次分流到 `DepositKytVerdictHandler`（Approved/Rejected/AwaitingUser/OnHold）→ 调 `DepositWorkflowService.applyKytVerdict()` 驱动充值状态机（Created 只记 debug 回执 no-op，Reviewed 归一 ignore，未知 type 记 orphan warn）。`applicantAction*` 事件**不**进这条新分支——走下一条的 `applicantActionReviewed` 统一前置分流（2026-08-18 订正：此前这里写"仍走 Clue 3 老分支"，Clue 3 已随材料请求账退役为死码，见下一条）；充值侧对材料补齐后的重检不需要专门 handler 接住 action 事件本身，客户补料后 Sumsub 自动重评发出的仍是 `applicantKytTxn*`，继续走新分支。详见 `v4-deposit.md` §4.1。
- **双域级联（2026-08-04 提现全流转 Task 4 落地；此前 §4 引用本节该段而本节漏写，2026-08-07 补）**：命中 `KYT_VERDICT_TYPES` 后**不是**只给 deposit——`DepositWebhookRouter.route()` 返回 boolean（是否有 deposit 拥有该 `kytTxnId`；ignore 类型也做归属查询），`depositHit=false` 时同一 payload 落到 `WithdrawWebhookRouter.route()`（`withdraw-sumsub/`，与 deposit 同构的第二棒）。两域按同一 `kytTxnId` 反查各自表，至多一家认领。事件表落 `dispatchedTo`：`DEPOSIT_SUMSUB` / `WITHDRAW_SUMSUB` / **`SUMSUB_KYT_ORPHAN`**（双都未认领的真孤儿独立标签，防止与真实路由混淆——ops 排查 dead-letter 时能区分"路由了"和"没人认"）；**孤儿 warn 只在级联最后一棒**（withdraw handler）打，deposit 侧"查无此单"已降为 debug（级联下它不再意味着孤儿）。锚点 `sumsub-ingestion.service.ts` dispatch 内 `depositHit/withdrawHit` 级联段 + `withdraw-sumsub/withdraw-webhook.router.ts`。
- **`applicantActionReviewed` 统一前置分流（2026-08-17 材料请求账起，取代原「先问 swap 认不认、不认再落材料重检」的顺序尝试链）**：Task 13 落地时这里还是一条 else-if 链——先转交 `SwapWebhookRouter.route()` 按 `CustomerMain.pendingActionExternalId` 认领，认不到再原样落回 Clue 3；因为同属一条 else-if 链，一旦命中就把下面 `ongoingDocExpired`/`inspectionId` 两条分支彻底遮蔽，原注释自陈是跨域收窄隐患，根因是没有统一 id 空间。**现在** `dispatch()` 在 Clue 1（`ongoingDocExpired`）之前新插一段——`depositWebhookType === 'applicantActionReviewed' && externalActionId` 就直接调 `MaterialRequestReviewService.applyReview({externalActionId, reviewAnswer, reviewRejectType})`：`externalActionId` 是 `material_requests` 的 `@unique` 列，一次查表即可定位归属（充值/提现/兑换/材料重检/等级升级五处下发口统一收在这一张表里），不用再猜、也不用按域顺序尝试。命中（`applyReview` 返回非 null）即消费，`dispatchedContext='MATERIAL_REQUEST'`；查不到（这个 `externalActionId` 不属于材料请求账，理论上不该发生，因为现在建 action 时统一由材料请求账铸 id）则 `result` 仍为空，继续往下走 Clue 1/2。裁决语义收在 `MaterialRequestReviewService.applyReview()` 里，三域共用同一份：GREEN → 落 `APPROVED`，若该行挂了便签（`restrictionNo` 非空）同事务内 `autoRelease()` 自动撕；RED 拆 `RETRY`（回 `PENDING_SUBMISSION`，两个 Sumsub id 原样不变，便签不撕）与 `FINAL`（终态 `REJECTED`，便签不撕）。兑换域专属的硬线 sticky 判断（`hardLineDispositionedAt`）收窄成事后一次回调 `SwapApplicantActionHandler.noteHardLineHeld()`（GREEN 落地、且该客户曾被硬线过时补一条 `SWAP_ACTION_GREEN_HARDLINE_HELD` 审计，不影响撕不撕便签——硬线客户本就没登记过材料请求，没有 `restrictionNo` 可撕）。锚点：`sumsub-ingestion.service.ts` dispatch 内 `applicantActionReviewed` 分支 ｜ `identity/material-requests/material-request-review.service.ts → applyReview()` ｜ `swap-sumsub/applicant-action.handler.ts → noteHardLineHeld()`。详见 `v2-customer-compliance.md` §2、`v4-deposit.md`/`v5-withdraw.md`/`v6-swap.md` 各自 §4.6/流程节，与设计稿 `doc-final/superpowers/specs/2026-08-17-material-request-ledger-design.md`。
