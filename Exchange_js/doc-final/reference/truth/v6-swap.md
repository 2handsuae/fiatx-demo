## 0. 一句话定位

平台内兑换（crypto↔fiat 余额交换）：报价 → L1 资格 + 限额门 → 消费 Quote → **建单 COMPLIANCE_PENDING（零记账）** → Sumsub KYT webhook 裁决落地 → approved 则 4 腿实时记账 → SUCCESS；rejected 则终态 REJECTED，客户本人命中制裁（`SANCTION_APPLICANT`）则终态 FROZEN——两者**都零记账痕迹**（这是整个重设计的卖点——不像充值钱已到暂扣户、提现资金已 pending-locked，兑换在裁决前压根没动过钱，拒绝不需要任何回滚）。**"平台内"= 在我方掌控的账户体系内做真实转账**——每腿跨钱包移动、有真实 externalRef（crypto→txHash / fiat→referenceNo，由 funds_order 在 CONFIRMED 铸、postLeg→enrichForPost 盖进 evidence）；**非**"纯账面划拨/无外部穿越"（旧口径已纠）。合规 = **L1 同步 eligibility/限额门 + L2 单笔 Sumsub KYT webhook 闸**（无 L2 Travel Rule/无大额审批门——因**无第三方对手方**，与充值/提现的三层合规刻意不同；出账腿走 KYT 送检，买入腿只喂纯数据不承载裁决）。**不**管：上链广播（模拟系统无真实外部 API）。

## 1. 状态机

`SwapTransactionStatus` 枚举 7 态，**5 态运行时可达**（2026-08-20 制裁分主体新增 `FROZEN`；`FAILED`/`REVERSED` 是历史兼容的不可达死枚举，见 BACKLOG「V6 兑换 FAILED/REVERSED 死枚举」）：
```
COMPLIANCE_PENDING ──(建单，零记账)──┐
COMPLIANCE_PENDING ──(KYT approved)──→ PROCESSING ──(4 腿全 CLEAR)──→ SUCCESS
                                       PROCESSING ──(腿失败)──→ 自愈重试(attempt+1，≤MAX_LEG_ATTEMPTS)──→ STUCK(needsReview + 手动 resume)，仍 PROCESSING
COMPLIANCE_PENDING ──(KYT rejected / SLA 超时)──→ REJECTED（终态，零记账）
COMPLIANCE_PENDING ──(KYT rejected 且客户本人命中制裁 SANCTION_APPLICANT)──→ FROZEN（终态，零出边，零记账）
```
- **出生态 = `COMPLIANCE_PENDING`**（Task 4 起，取代旧版直接建 PROCESSING+leg1）：`initiateSwap()` 只建 swap 行 + 消费 Quote，**不建任何 funds_order、不碰 TB**。leg1 只在收到 approved 裁决时才建（`applyKytVerdict()` 内）。
- **裁决落地窗口**：swap 处于 `PROCESSING` 期间迟到的裁决（腿还在结算，Sumsub 复核较慢）**不驱动状态机**（PROCESSING 无 KYT_*/FREEZE 合法边），只落证据字段 + `needsReview`（rejected 时）+ 专属审计，然后照常继续结算；若迟到裁决是 rejected（含制裁命中），仍会跑一遍处置（限制客户能力），但不会试图撤销已经在走的兑换、也不会把单子打进 FROZEN——`PROCESSING` **刻意不设 FREEZE 入边**：四条腿正在逐条过账，半程冻结会把账本劈成两半（钱已经离开了 A 账、还没到 B 账）。
- **`FROZEN`（2026-08-20 起活态，零出边终态）**：唯一入边 `COMPLIANCE_PENDING --FREEZE--> FROZEN`，只在 KYT 裁决的 `typedTags` 命中 `SANCTION_APPLICANT`（客户本人被制裁，判据 `hasApplicantSanctionHit()`）时触发；`hasApplicantSanctionHit()` 只认 `SANCTION_APPLICANT` 是防御性写法——兑换是平台内 crypto↔fiat 余额交换，钱在我方账户体系内部动，没有第三方对手方，Sumsub 不可能对一笔 swap 回传"对手方被制裁"，`SANCTION_COUNTERPARTY` 在本域**不会出现**（业主 2026-08-20 终审裁定；对应 demo fixture 按钮 `V4B_REJECTED_SANCTION_COUNTERPARTY` 已删——充值/提现两域有真实外部对手方，场景成立，保留同名按钮）。两个驱动方：① 本单自己的 KYT 裁决（`applyKytVerdict()` 尾部，先落证据、不 markStatus，FREEZE 由 `handleRejectDisposition()` 内"先冻人再冻单"的 fail-safe 顺序落地）；② 跨域冻人广播（`onCustomerRestrictionOpened()`，只认 `cause==='SANCTION'`——`ADMIN_SUSPENSION` 等同为 `scope=['ALL']` 的行政便签会广播同一事件，但不该把单推进零出边终态，见 §3.6）。已 `FROZEN` 的单再收裁决，`applyKytVerdict()` 顶部的幂等闸直接 no-op + 写 `SWAP_KYT_VERDICT_IGNORED` 审计（防死信——Sumsub 重投同一条 rejected webhook 若无此闸会撞上零出边终态抛 `Invalid transition`）；主路径 FREEZE 若因广播抢先而 `markStatus` 抛错，重读状态已是 `FROZEN` 判良性竞态（fall-through 继续走 sticky 标记与处置审计），不判真失败。`completedAt` **只在 SUCCESS 时写**——FROZEN 与普通 REJECTED 均为 `null`，是客户面"分不出"的隐含前提之一（另一半在 §3.6a 的状态收敛）。
- ⚠️ **`FAILED` / `REVERSED` 是死枚举**：定义在 `SwapTransactionStatus`，但**全代码无一处 `markStatus` 设置它们**（`markStatus` 只被 `'SUCCESS'`/`'kyt_approved'`/`'kyt_rejected'`/`'sla_breach'`/`'freeze'` 调用）。失败**永不**转 FAILED（注释原文 "never markStatus FAILED"），**无 reverse 端点**转 REVERSED。
- 锚点：`swap-transaction.dto.ts → SwapTransactionStatus/SwapTransactionAction` ｜ `swap-transactions.service.ts → transitions`（合法边表）/`SWAP_TERMINAL_STATUSES`/`SWAP_FREEZE_SCAN_EXCLUDED`/`SWAP_CUSTOMER_STATUS_PASSTHROUGH`（见 §3.6a/§3.6b） ｜ `swap-workflow.service.ts → initiateSwap()/applyKytVerdict()/handleRejectDisposition()/hasApplicantSanctionHit()/onLegFailedSelfHeal()/onCustomerRestrictionOpened()`（自愈+STUCK+冻结两个驱动方）

## 3. 关键流程

- **报价**：`SwapQuoteService.createQuote()` → `resolveBestLevel()`（多 level 取最低费）+ `BinanceRateProvider.fetchRate()`（实时 + 3s 缓存 + AED 钉 3.6725）+ `PricingEngineService.buildSwapQuote()`（amountOut/spread/fee）→ 30s TTL
- **L1 资格**：`SwapWorkflowService.initiateSwap()` 内 `ensureCustomerCanTransact()` + `assertTradingEligibility(ownerId, 'SWAP')`（pre-creation 同步；`restrictions` 含 `SWAP` 时在此拦，403）
- **L1 金额限额门**（资格之后、`$transaction` 之前）：`initiateSwap()` 事务外 peek quote（`swapQuote.findUnique` 取 `fromAssetId`/`amountIn`）→ `TransactionLimitGateService.evaluate({operationType:'SWAP',customerId:ownerId,assetId,amount})`——A 单笔 min/max（原生币种）+ B 周期累计（AED，迪拜日历日/月窗口，用量 = 窗口内该客户 swap `grossAedValue` 之和[排除 FAILED/REVERSED] + 本笔）；有 B 规则但汇率失败 → fail-closed `UNPRICEABLE`。拒绝 = **swap 不建、quote 不耗**，审计 `TRANSACTION_LIMIT_REJECTED`（workflowType `TRANSACTION_LIMIT_ENFORCEMENT`）；通过则 `grossAedValue` 随 swap 行落库。peek 到空 quote 不在此抛（落到事务内 `getActiveQuoteOrThrow` 的既有 SWAP_FAILED 路径）。**无 D1 大额审批门**（业主决策：兑换资金不出境、无第三方对手方，不做大额审批）
- **R4 双边收款账户门**：`initiateSwap()` 读到 quote 后（事务内，consume 前）逐一检查 buy/sell 两侧资产的 `WalletQueryService.hasReceivingAccount(ownerId, assetId)`（ACTIVE 的 C_DEP/C_VIBAN），任一缺失即 `RECEIVING_ACCOUNT_REQUIRED`（带 assetCode），先于 consumeQuote/建 swap 行拦截，避免裁决通过后才在 `buildLegContext()`/`resolveLegWallets()` 撞见钱包缺失
  - **前端逐币预检**（`Swap.tsx` + `GET /client/trading-readiness/receiving-accounts`）：选定 buy/sell 后即查两侧收款账户，缺失则禁提交并提示，CTA「Create receiving account」**跳 `/deposit`**（收款账户=充值地址，Deposit 页是自然落点；2026-07-11 起，原 `/wallet`）
- **建单 = 零记账**（Task 4 重设计）：`initiateSwap()` 通过上述三道门后，事务内只做 consume Quote + 建 swap 行（`COMPLIANCE_PENDING`），**不建 leg1、不碰 TB**；事务外 `submitSumsubTxnOut()` 同步 awaited 把出账腿（fromAsset，direction=out）送 Sumsub KYT——**整个 initiateSwap 调用期间零 TB 写入**，客户端拿到的响应已经是终态之一的前置态。`submitSumsubTxnOut` 全程 try/catch（I2 教训）：Sumsub 不可达时静默留 `COMPLIANCE_PENDING` 等重试（SLA 看门狗兜底），绝不 500 客户
- **KYT 裁决落地 = `SwapWorkflowService.applyKytVerdict()`**（webhook 驱动，`SwapKytVerdictHandler` 调用；三分支）：
  - `approved` → 同一事务内 `markStatus(KYT_APPROVED)`→`PROCESSING` + `buildLegContext()` 重建记账上下文 + `createLeg(leg1)`；事务外 fire-and-forget `submitSumsubTxnIn()` 补喂买入腿（纯数据，不承载裁决，失败不阻断已放行的兑换）
  - `rejected` 且**客户本人命中制裁**（`typedTags` 含 `SANCTION_APPLICANT`，判据 `hasApplicantSanctionHit()`）→ 事务内**跳过** `markStatus(KYT_REJECTED)`，只落证据；FREEZE 由事务外的 `handleRejectDisposition()` 按"先冻人（`customerRestrictionsService.open`）、再冻单（`markStatus(FREEZE)`）"的顺序落地 → `FROZEN`，**不建任何 leg、不碰 TB**（迁移表里 `REJECTED` 零出边，若先落 `REJECTED` 再"补冻"会撞 `Invalid transition`，故这里判定必须先于 markStatus）
  - `rejected` 且未命中客户本人制裁 → 同一事务内 `markStatus(KYT_REJECTED, {rejectReason:'KYT_REJECTED'})`→`REJECTED`，**不建任何 leg、不碰 TB**；随后（事务外）`handleRejectDisposition()` 处置客户能力（对手方命中 `SANCTION_COUNTERPARTY` 也走这条分支——只终态 REJECTED，不冻人，按软/硬线判定登记材料请求）
  - `PROCESSING` 期迟到裁决 → 不驱动状态机（见 §1），只落证据 + `needsReview`（rejected 时）+ 专属审计
  - **终态忽略补审计（第一批 · 2026-08-19，`SWAP_KYT_VERDICT_IGNORED`）**：兑换本来就是「先判后写」——`applyKytVerdict()` 开头即 `KYT_VERDICT_TERMINAL_STATUSES.has(status)`（`SUCCESS`/`REJECTED`/`FAILED`/`REVERSED`）判定，本轮**未重构判定顺序**，兑换域**没有** `decideVerdictLanding()`（不要照抄充值/提现的三段式写法）。改动只是在这段既有的终态 no-op 分支尾部新增一次私有 `recordVerdictIgnored()` 调用，强制写 `SWAP_KYT_VERDICT_IGNORED` 审计（`requestId` 拼 `randomUUID()`——业主 2026-08-19 拍板：N 次写 N 行，来了几次本身是证据；`.catch` 记 `logger.error`，不哑吞）。**调用点必须落在 `(REJECTED||SUCCESS) && verdict==='rejected'` 的处置 carve-out 判断之后**——那段 carve-out（redelivery/重投场景，见其注释）命中时会跑 `handleRejectDisposition()`（写 `SWAP_KYT_REJECTED_DISPOSED`）并提前 `return`，走不到 `recordVerdictIgnored()`；若把审计调用挪到 carve-out 之前，同一个 webhook 事件会既落一条"已忽略"又落一条"已处置"，自相矛盾。carve-out 未命中（例如已 `SUCCESS`/`REJECTED` 又收到 `approved`，或已 `FAILED`/`REVERSED` 收到任何裁决）才会走到 `recordVerdictIgnored()`。
- **拒绝处置 = `handleRejectDisposition()`**（`swap-workflow.service.ts`，跑在裁决事务外，全程独立幂等——webhook 可能重投；**2026-08-18 订正**：登记机制已随材料请求账重写，见下；**2026-08-20 制裁分主体**：cause 判定改读类内私有谓词 `hasApplicantSanctionHit(typedTags)`，即 `typedTags.includes('SANCTION_APPLICANT')`）：无条件先按分型定 cause 开限制账便签（`CustomerRestrictionsService.open({cause})`，不再是旧 `restrictions.add(capability[])` JSON 数组写法；**从不限 DEPOSIT**——链上资金已到账，拒收不解决问题）——**只有** `hasApplicantSanctionHit()` 为真（客户本人被制裁）→ cause=`SANCTION`（SILENT，卡全部能力，只能 MLRO 解，`caseRef` 传 `swapNo` 只为可读，`CustomerRestrictionsService.openWithin` 会把它归一成 `customerNo`——`SANCTION` 是客户级因由，同一客户无论被几笔单牵出来永远只有最早的那一张 OPEN，第 2..N 次命中 `created=false`、不广播、但仍写一条 `result=SKIPPED` 的审计，详见 `restriction-cause.constant.ts → RESTRICTION_CAUSE_POLICY.SANCTION.customerLevel` 与 `customer-restrictions.service.ts → openWithin()`）；对手方命中 `SANCTION_COUNTERPARTY`（不算硬线制裁）与无制裁的普通拒绝，一律按本次是否暴露补料入口分 `KYT_REJECTED_SOFT`（DISCLOSED）与 `KYT_REJECTED_HARD`（SILENT），`caseRef=swapNo`（这两个 cause 非客户级，不归一，按单撕）。再按分型登记材料请求——**从 `CustomerPendingActionService.set()` 单值指针换成 `MaterialRequestIssuerService.register()` 逐条登记**（旧写法同一客户第二笔单软线拒会把第一笔整个盖掉，现在一条 action 一行，各交各的、各撕各的）：
  - **软线**（有 ≥1 个 `applicantActions` 且非客户本人命中制裁，且该客户从未被硬线过）→ 登记一行材料请求并挂上刚开的便签（`restrictionNo`），客户端 `GET /client/me/material-requests` 可见
  - **硬线**（无 action 可做，或客户本人命中制裁，或该客户曾被任意一笔 swap 硬线过）→ **不登记材料请求**（tipping-off——大多数 AML 法域下告知客户涉制裁调查是刑事犯罪，SILENT 类 cause 不该有一个能点进去的认证入口，见 `MaterialRequestIssuerService.resolveCause()`）；命中客户本人制裁时额外盖 `hardLineDispositionedAt` 硬线 sticky 标记，**永久**沉默该客户此后任何一笔（哪怕本身是软线的）裁决的补料入口，跨订单持久
  - **`COMPLIANCE_PENDING --FREEZE--> FROZEN`（客户本人命中制裁时的落地边，2026-08-20）**：顺序在 `open()` 之后（先冻人、再冻单，与充值/提现一致的 fail-safe 排列），只在 `swap.status===COMPLIANCE_PENDING` 时执行（`PROCESSING`/终态无 FREEZE 合法边，见 §1）；`markStatus(FREEZE)` 若因跨域广播抢先而抛错，重读状态已是 `FROZEN` 判良性竞态，fall-through 继续走 sticky 标记与 `SWAP_KYT_REJECTED_DISPOSED` 审计，不判真失败；`REJECTED`/`SUCCESS` carve-out（见上方"终态忽略补审计"条）允许对已终态的单重跑本方法（只重跑处置，不重跑 markStatus/建腿），但 `FROZEN` 不在这个 carve-out 里——`FROZEN` 单再收裁决在 `applyKytVerdict()` 顶部就被幂等闸拦下（见 §1），压根到不了这里，故已冻结的单收到重投的制裁裁决**不会**重跑处置（与 `REJECTED` 的"单已终态≠处置已落地，允许重跑"不对称，本批裁定不改，见 BACKLOG）
- **人身层闭环 = `MaterialRequestReviewService`**（Task 4，2026-08-17 材料请求账起三域共用同一套逻辑；`SwapApplicantActionHandler` 退化为仅剩 `noteHardLineHeld()` 一个回调）：webhook 按 `externalActionId` 反查 `material_requests` 行（**不再靠 `pendingActionExternalId` 单值指针认领**）——GREEN → `markReviewed()` 落 `APPROVED`，若该行挂了便签（`restrictionNo` 非空）同事务内 `autoRelease()` 自动撕（硬线客户的便签撕不掉，因为硬线时压根没登记过材料请求、没有 `restrictionNo` 可挂）；GREEN 落地后回调 `SwapApplicantActionHandler.noteHardLineHeld()`——若该客户曾被硬线过，记一条「GREEN 到过、限制仍被刻意保留」的审计（`SWAP_ACTION_GREEN_HARDLINE_HELD`），供调查员核验；RED 拆 `RETRY`（回 `PENDING_SUBMISSION`，`applicantActionId`/`externalActionId` 原样不变，限制不撕）与 `FINAL`（终态 `REJECTED`，限制同样不撕）——旧模型把所有 RED 都当"限制原样保留、指针不清"，不区分能不能重交，本表以 `onboarding.service.ts` 原有的 RETRY/FINAL 区分为准

## 3.6 制裁分主体：四个状态判据的 FROZEN 归属

`FROZEN` 落地后，兑换域原有的四个状态判据集合各自要不要把它算进去，答案并不一致——同一个"FROZEN 算不算"的问题在四处分别有相反的正确答案，是这次改动里最容易做错的地方：

| 判据 | 常量 | FROZEN 在内？ | 为什么 |
|---|---|---|---|
| 「单据生命周期已结束」 | `SWAP_TERMINAL_STATUSES`（`swap-transactions.service.ts`） | **否** | 进去会被材料请求作废监听器当成终态撕掉客户在途的材料请求卡片——被制裁调查的客户，撕掉=客户端一个可感知的变化=tipping-off |
| 「不需要再被冻结广播捞起」 | `SWAP_FREEZE_SCAN_EXCLUDED`（=`SWAP_TERMINAL_STATUSES` ∪ `{FROZEN}`） | **是** | 已经冻了的单不必再冻一次；与上一行故意相反，两个判据回答的是不同问题 |
| KYT 裁决终态忽略判定 | `KYT_VERDICT_TERMINAL_STATUSES`（`swap-workflow.service.ts` 类内私有） | **否** | 兑换域**没有** `decideVerdictLanding()`（不要照抄充值/提现的三段式写法）——不放进集合，改在 `applyKytVerdict()` 顶部另写一段守卫：`if (status === SwapTransactionStatus.FROZEN) { await this.recordVerdictIgnored(swap, input, status); return; }`（`swap-workflow.service.ts:517-521`，§1）——语义不同："终态所以忽略" vs "冻了所以忽略"，混在一起以后没人分得清 |
| 客户面状态收敛白名单 | `SWAP_CUSTOMER_STATUS_PASSTHROUGH`（`swap-transactions.service.ts`） | **否** | `FROZEN` 不在白名单里，经 `toCustomerSwapStatus()` 显式收敛成 `REJECTED`（下方「客户面三层防线」条） |

## 3.7 兑换客户面三层防线（2026-08-20）

制裁冻结对客户必须"零痕迹"——客户看到的应该与一次普通的 KYT 拒绝逐字相同。三层防线，逐层核对代码：

1. **响应体收敛**：`toCustomerSwapView()`（`swap-transactions.service.ts`）里 `status` 字段先经 `toCustomerSwapStatus(raw)` 收敛才输出——白名单 `SWAP_CUSTOMER_STATUS_PASSTHROUGH`（`COMPLIANCE_PENDING`/`PROCESSING`/`SUCCESS`/`REJECTED`）原样透传，`FROZEN` 显式收敛成 `REJECTED`（客户看到 'Unsuccessful'，与普通拒绝无区别），白名单外的其余任何值（含未来新增状态）一律收敛成 `COMPLIANCE_PENDING`——宁可错杀。这一收敛与充值的选择**故意不同**：充值 `FROZEN` 是可逆的（`RESUME`→`COMPLIANCE_PENDING`），收敛成"处理中"是诚实的；兑换 `FROZEN` 是零出边终态，收敛成"处理中"会是一句永远不会兑现的谎，还会让客户端自刷定时器永不停止。
2. **筛选面按收敛后的值展开**：`findAll({customerScope:true})` 的 `status` 查询参数不再是"原始值精确匹配"，而是先把入参展开成"所有会被 `toCustomerSwapStatus` 收敛成这个值的原始状态集合"（`Object.values(SwapTransactionStatus).filter(raw => toCustomerSwapStatus(raw) === status)`），再拿这个集合去 `where.status = {in: expanded}`。筛 `REJECTED` 会同时匹配 DB 里的 `REJECTED` 和 `FROZEN`（两者客户面看起来都是 'Unsuccessful'）；筛 `FROZEN` 本身展开为空集，`{in: []}` 精确返回零行——不报错（报错本身可探测）、不退化成全量（那是另一种可探测信号），与"筛了一个真实存在但恰好没有命中记录的状态"响应完全相同。
3. **展开集合从收敛函数派生，不手工维护平行表**：早前（Task 10）`customerScope` 下曾是"完全忽略 `status` 参数"，堵住了探测面但也打哑了 `Swap.tsx` 真在用的 History 筛选下拉；也考虑过手写一张 `{REJECTED: [REJECTED, FROZEN]}` 平行表，但手写表必然与 `toCustomerSwapStatus()` 漂移（教训见 `deposit-transactions.service.ts` 的"白名单枚举必然滞后于状态机"）。现在的写法让任何新增状态天生落进正确的桶，没人需要记得同步两处。

**前端零改动**：`client-web/src/pages/Swap.tsx` 只认 `REJECTED`/`SUCCESS`/`PROCESSING`/`COMPLIANCE_PENDING` 四个值，`REJECTED` 早已映射成 'Unsuccessful' 且在其终态集合内——`FROZEN` 收敛成 `REJECTED` 后客户端不需要任何改动就能正确展示。

## 3.8 SLA 计时（第三批，2026-08-21 落地）

两个字段（`SwapTransaction` 表）：`slaDeadline`（截止时刻，`DateTime?`）、`slaBreached`（已超时标记，`boolean`）。与充值/提现域同名同型，实现独立一份（deliberate fork）。

- **配置表** `SWAP_SLA_MINUTES_BY_STATUS`（`swap-transactions.service.ts:115-117`）**只有一格**：`COMPLIANCE_PENDING` = 5 分钟（等 Sumsub 回裁决）。兑换**没有软 SLA**——它没有"等自己人"的状态（无人工复核态、无审批门），`findSlaBreachCandidates()` 只查 `COMPLIANCE_PENDING`。此前是硬编码常量 `SWAP_COMPLIANCE_TIMEOUT_MS=60_000`（60 秒，未经真实 Sumsub 延迟校准），2026-08-21 业主裁定改成与充值/提现的 `COMPLIANCE_PENDING` 硬 SLA 同一个数字——"三域等的都是同一件事（Sumsub 回裁决），没有理由分三个数"。
- **收口点**：私有 `resolveSlaFields(nextStatus)`（`:475-480`）在两处收口——`create()`（建单，`:862-936`，注释原文"建单不走 markStatus，收口处覆盖不到——这里按同一张配置表补上，保证进入 COMPLIANCE_PENDING 就开始计时对建单这条路也成立"）与 `markStatus()`（状态迁移，`:580-589`）。**兑换从 `createdAt` 改成按 `slaDeadline` 计时**（此前算的是"这单建了多久"，现在算的是"在这个状态待了多久"）——今天 `COMPLIANCE_PENDING` 是出生态，两者结果等价，但只要多一条进入该状态的路径（当前尚不存在），两种口径就会分道，故按状态计时是唯一站得住的口径。
- **无 reissue 分支**：兑换没有 `awaitUser` 语义（无补料流程），故不存在充值/提现那样的"状态不变但要重算 deadline"的例外出口，`resolveSlaFields()` 保持私有，未对外暴露。
- **硬破线不传 `slaBreached: true`**：`SwapSlaService.sweep()` 判超时后 `markStatus(SLA_BREACH)` 推 `REJECTED`，不显式设 `slaBreached`——`REJECTED` 不在配置表内，`resolveSlaFields()` 收口处天然把 `slaDeadline` 清 `null`，天然不再匹配 `findSlaBreachCandidates()` 的 `slaDeadline < now` 条件，无需手动置标记防重复扫（与充值/提现"避免覆盖新计时器"的理由不同——兑换没有新计时器可覆盖，`REJECTED` 是零出边终态）。
- **超时不触发客户处置**：见 §1/§3 类注释原文——`sweep()` 判超时之后**不**调用 `handleRejectDisposition()`（限制客户能力那一套）。超时只说明 Sumsub 没能在窗口内回话，跟客户是否可疑毫无关系；套用 KYT 拒绝那套限制等于把平台自己响应慢的锅记到客户账上。
- **`sumsubTxnIdOut` 为空的分支不是超时，是漏提交**：`submitSumsubTxnOut()` 提交失败被设计成非致命（不让客户因 Sumsub 抖动吃 500），`sweep()` 扫到这类单会重试提交而非直接判死。
- **审计与 `requestId`**：`SwapSlaService.sweep()` 写的 `SWAP_SLA_BREACHED` 审计**未**拼 `requestId`（与充值/提现两域、以及本域 `setSlaDeadlineByNo()` 的 `SWAP_SLA_TIMEOUT_SIMULATED` 演示审计不同——后者拼了）；`REJECTED` 是零出边终态，同一笔 swap 不会被扫描器二次匹配到同一 `action`，故无需 `requestId` 防幂等键静默去重这层保护。
- **演示触发**：`SwapTransactionDetail.tsx` action 栏「模拟超时」按钮（与 ⚡ Simulation 面板物理分离）调 `POST :swapNo/simulate-sla-timeout` → `setSlaDeadlineByNo()`；`slaDeadline===null` 时拒绝。该端点新增了 `assertAdmin()` 守卫（`swap-transactions.controller.ts` 此前无此私有方法，本批新增）；但控制器既有的 `advanceSwapLeg()`/`resumeSwapLeg()` 两端点**仍缺**同款 `assertAdmin()`（只有 `@RequirePermissions` 装饰器，`AdminPermissionGuard` 对非 ADMIN token 会 no-op 放行——本批按仓库先例只给新增端点加闸，旧洞未修，见 BACKLOG）。
- **前端展示**：`admin-web/src/utils/slaDisplay.ts → formatSlaRemaining()`（三域共用同一份格式化函数）；`SwapTransactionList.tsx` 加剩余时间列 +「仅看已超时」复选框（前端过滤，只对当前页生效，后端无对应查询参数，见 BACKLOG）；`SwapTransactionDetail.tsx` 渲染倒计时/超时红标。
- **客户端不显示**：`slaDeadline`/`slaBreached` 不在 `toCustomerSwapView()` 白名单内，tipping-off 防线的一部分。
- **锚点**：`swap-transactions.service.ts`（`SWAP_SLA_MINUTES_BY_STATUS`/`resolveSlaFields()`/`create()`/`markStatus()`/`findSlaBreachCandidates()`/`setSlaDeadlineByNo()`）｜ `swap-sumsub/swap-sla.service.ts`（`SwapSlaService.sweep()`，`@Cron('*/30 * * * * *')`）｜ `swap-transactions.controller.ts → simulateSlaTimeout()`（`assertAdmin()`）｜ `admin-web/src/utils/slaDisplay.ts` ｜ `admin-web/src/pages/SwapTransactionList.tsx`/`SwapTransactionDetail.tsx` ｜ `test/sla.e2e-spec.ts`（三域共 7 例，兑换覆盖硬破线推 `REJECTED` 一例）
