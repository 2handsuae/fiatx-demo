## Permission Code Format

Permission codes are generated by `buildPermissionCode(method, path)` in `permission-code.util.ts`:

```
api.<method_lowercase>.<normalized_path>
```

Path normalization (`normalizePermissionPath`):
- Strip query string, leading/trailing slashes
- Each segment: strip leading `:`, replace `*` → `wildcard`, replace non-alphanumeric chars → `_`, lowercase
- Join segments with `_`

Examples:
- `GET /admin/iam/roles` → `api.get.admin_iam_roles`
- `PUT /admin/iam/users/:id/roles` → `api.put.admin_iam_users_id_roles`
- `POST /admin/audit-logs/export/evidence-package` → `api.post.admin_audit_logs_export_evidence_package`

## Key Business Rules

- Permission records are seeded and managed via `rbac.catalog.ts` (`RBAC_PERMISSION_DEFINITIONS`). The DB is the authoritative store; the catalog is the source of truth for seeding.
- `RBAC_PERMISSION_CODE_SET` is a runtime Set of all catalog permission codes used by `isManagedPermission()` to distinguish catalog-managed permissions from any legacy entries.
- `AdminPermissionGuard` resolves the requesting user's permission codes via `getUserPermissionCodes()` and checks against the code required by `@RequirePermissions(code)` decorator on each route handler.
- `SUPER_ADMIN` users bypass the permission DB lookup — the guard short-circuits to `true` for all codes.
- Permission assignment to roles is indirect: `RBAC_ROLE_GROUP_BINDINGS` maps role codes to `PermissionGroup[]`; at seed time, `buildRolePermissionCodeMap()` resolves the full permission code list per role and inserts `RolePermission` rows.
- A permission may belong to multiple groups. Permissions are unioned across all groups when computing role permission sets.
- No API exists to create, update, or delete Permission records at runtime — permissions are catalog-managed and immutable outside of seeding.

## Service Methods (key operations)

- `listPermissions()` — DB query: returns all Permission rows ordered by code
- `listCatalogPermissions()` — returns `RBAC_PERMISSION_DEFINITIONS` in-memory without DB; used to surface the catalog definition
- `getUserPermissionCodes(userId)` — resolves effective permission codes by traversing UserRole → Role → RolePermission → Permission; SUPER_ADMIN fast-path returns all catalog codes
- `hasPermission(userId, permissionCode)` — checks if the user's effective permission set includes the given code
- `isManagedPermission(permissionCode)` — returns true if the code exists in `RBAC_PERMISSION_CODE_SET`
- `buildRolePermissionCodeMap()` — utility used at seed time; returns `Record<roleCode, permissionCode[]>` for all roles

## API Endpoints

| Method | Path | Permission Group | Description |
|---|---|---|---|
| GET | /admin/iam/permissions | IAM_READ | List all permission records from DB |
| GET | /admin/iam/roles | IAM_READ | List roles with their bound permissions (includes permission details inline) |

Note: Permissions are not individually manageable via API. The `GET /admin/iam/permissions` endpoint exposes the DB-seeded catalog. Role-to-permission bindings are established at seed time and refreshed via DB migrations / seed scripts — not via runtime API calls.
