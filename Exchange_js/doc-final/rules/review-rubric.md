# 演示专用评审表（review-rubric）

评审只判三件事。三件之外的**一律不算缺陷**——发现了就在 `doc-final/PRODUCTION-NOTES.md` 记一行，评审报告里不出现。

## 三判据

| # | 缺陷类型 | 判据 |
|---|---|---|
| 1 | 业务逻辑不符 | `prd/` 说应该这样（未写则以 `test-cases/` 与 `modules/` 叙事为准），代码或页面不是这样 |
| 2 | 流程演示不出来 | 页面缺、状态到不了、数据看不见、结局讲不圆 |
| 3 | 代码读不懂 | 命名不业务、一个流程被拆散在多处、workflow 读不出 PRD 步骤 |

## 业务规则 vs 技术兜底判定表

| 例子 | 判定 | 理由 |
|---|---|---|
| 客户不能提走超过可用余额的钱 | 业务规则，做 | PRD 会写；演示提现时一定讲到 |
| 被冻结/被调查的客户在客户端只看到"合规审核中" | 业务规则，做 | tipping-off 是合规流程的一部分，演示要讲 |
| 大额提现要过 SMO 审批门 | 业务规则，做 | 决策点与角色 |
| 管理端接口能被普通客户令牌调用 | 技术兜底，不做 | 只在攻击场景触发；演示假设管理员善意 |
| 同一 txHash 可能生成两笔充值 | 技术兜底，不做 | 只在外部系统重复回调时触发；演示假设只回一次 |
| Sumsub 回调重放导致重复入账 | 技术兜底，不做 | 同上 |
| 单号随机位不足偶发唯一约束冲突 | 技术兜底，不做 | 并发/概率问题 |
| `emit` 改 `emitAsync` 让异常传播 | 技术兜底，不做 | 故障场景 |
| 记账失败后没有 repair surface | 技术兜底，不做 | 故障恢复 |
| 状态机缺一条"退回发起方"的终态 | 业务规则，做 | 结局不完整，演示讲不圆 |
| 审计日志缺某个业务动作 | 业务规则，做 | VARA 场景下审计是业务可见物 |

判定口诀：**PRD 里写得出来的做；只有攻击者、故障或并发才会触发的不做。**

## 评审纪律

- 不以"生产环境会怎样"为由立缺陷。
- 判定表右列（技术兜底）类发现 → PRODUCTION-NOTES 一行，不进评审结论。
- 测试的绿必须来自行为：发现「扫源码文本」型断言（注释就能喂饱的），按第 3 条立缺陷。
- 评审报告 ≤ 50 行；每条缺陷必须写清"**演示到哪一步、观众会看到什么错**"。
