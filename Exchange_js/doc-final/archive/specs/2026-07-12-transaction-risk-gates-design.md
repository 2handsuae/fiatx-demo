# 设计 · 交易风控三闸门（L1 初始 / L2 专属 / L3 行为监测）

Date: 2026-07-12 ｜ Status: Draft（设计稿，**只出设计不实现**）｜ 来源: brainstorming（本会话）

> 定义订单级交易风控的统一框架：三个闸门（L1/L2/L3）× 三种订单（充值/提现/兑换）的拦截时点、执行方、命中动作与处置模型。
> **范围声明**：本文是**架构与模型设计稿**，不含实现计划（业主 2026-07-12 定：只写 spec）。落地时另开 worktree 走 writing-plans。
> **自研边界**：除"客户状态/限额/余额"等自有数据库校验（L1）外，KYT/TR/行为监测**全部用 Sumsub**，平台不自建风控引擎。

## 2. 核心模型：三闸门定义

| | **L1 初始闸门** | **L2 专属闸门** | **L3 行为监测** |
|---|---|---|---|
| 查什么 | 客户三轴态、restrictions、**限额**、余额、地址白名单/收款账户就绪 | KYT（链上地址风险）+ Travel Rule + 大额审批门 | 跨单行为模式（拆单/快进快出/对倒/休眠突爆/账号接管） |
| 谁执行 | **平台自己**（几条 SQL，非"引擎"） | **Sumsub**（+大额门是平台自有审批流；+法币人名核对是运营人工） | **Sumsub TM**（平台只建告警承接层） |
| 时效 | 毫秒 | 秒~分钟（订单挂起等回执） | 分钟~天（旁路异步） |
| 拦截性质 | **闸门**（门：过/不过） | **闸门**（唯一阻塞筛查） | **不是闸门，是摄像头**（事后侦测，产出告警） |
| 命中动作 | 拦下（提现：单不建；充值/兑换见 §4） | 自动放行 / FROZEN 转 MLRO / ACTION_PENDING 补料 | 生成 record→case，**处置人/钱**，不拦当下这笔 |

**关键判据**（哪些规则落哪层，由"谁执行 + 要多快 + 数据窗口"决定，不由规则复杂度决定）：
- 一条简单查询毫秒内能算完、且平台自己跑 → **L1**。
- 需外部 KYT/TR、或用 Sumsub 即时规则（含滚动累计的频率规则，提交时即命中可挡单）→ **L2**。
- 需 Sumsub AI 异常检测 / 团伙聚类 / 回看全局模式（数学上无法在当笔命中）→ **L3**。

> Sumsub 侧澄清（官方文档核实 2026-07-12）：TM 规则**全部在交易提交时评估**，无"即时/延迟"开关；频率/累计类靠**滚动计数器**能在当笔命中挡单（归 L2）；只有 AI 异常/团伙类才真正只能事后（归 L3）。KYT 在 Sumsub 里是 TM 的一个规则包（Crypto Monitoring），与行为监测同引擎、两种消费姿势。

## 4. 三种单 × 三闸门

三种订单结构不同，核心不对称是 **「钱先到还是单先建」**，它决定 L1 是"门卫"还是"分流器"。

### 4.1 提现（前 / 中 / 后，三段最全）

```
下单 ─L1─┬ 不过 → 单不建，前端报错（毫秒）
         └ 过 → CREATED，锁余额
              └ 大额门 ≥20万AED → 高管审批（平台自有流）
                   └ L2（挂起等回执）: KYT(收款地址去向) + TR
                        ├ 全 GREEN → 放行 → Payout → 链上广播
                        └ RED/命中 → FROZEN → MLRO 定夺
                             钱出去 → SUCCESS(终态)
                                  └ L3(旁路): 命中 → 管人（后续单挂起 + TR追索 + 上报），钱追不回
```
- **L1 是真实闸门**（拦=单不建）；订单上的 L1 是**通过时的证据快照**（回显）。
- KYT 方向：查**收款地址**（钱去哪）。
- **大额审批门**独立一道，订单展示需单列（≥20万 AED，V5 已实现）。
- L3 命中：**提现钱已走，主要管人**——但两点修正：① 速度快的频率规则应前移（L1/L2 当笔就挡，不必等事后）；② 事后仍有三招：后续提现全挂起人审、TR 通道联系对手所尝试冻结、上报监管。

### 4.2 充值（无"订单前"，L1 变分流器）

```
链上/银行到账（钱已到，拦截不存在）
  ├ 归属识别失败 → 孤儿充值，挂 suspense 人工（不入三闸门）
  └ 确认数够 → 钱记入【中转账户 DEPOSIT_SUSPENSE】（客户碰不到）
       ─L1─┬ 受限客户/渠道停 → FROZEN（不是拒单，钱都到了），L2 不启动（省KYT费）
           └ 过 → L2
                L2(挂起): KYT(付款地址来源) + TR(法币自动免) + 法币人名核对
                  ├ GREEN → 放行 → 中转账户→客户可用余额 → SUCCESS(终态)
                  ├ RED/制裁 → FROZEN → MLRO: 放行/没收/退回
                  └ 补料 → ACTION_PENDING（超时 EXPIRED，钱退回中转前）
                       └ L3(旁路): 未终态→置 FROZEN(钱还在中转，挡得住)；已终态→冻余额/客户
```
- **无订单前**（只有中/后两段）；L1 从拦截器变**分流器**（过→L2 / 不过→FROZEN）。
- KYT 方向**反转**：查**付款地址**（钱从哪来）。
- **无大额人工审批门**（收钱本身非风险动作，来路不明才是，靠 L2 规则 FROZEN→MLRO）。
- **金额管控白送**：SUCCESS 前钱挂中转账户，FROZEN 即天然管控，无需新原语。

### 4.3 兑换（哑铃型：L1 真门 + L3 重兵，无 L2）

```
报价（轻校验:货币对可用/能交易）→ 30s TTL → 确认成交
  ─L1─┬ 不过 → 单不建，报错（L1 跑在"确认成交"时点，不信报价旧结论）
      └ 过 → 消费报价 → 四腿记账 → SUCCESS(终态，全程秒级)
  ─L2─【无】资金不出境:无外部地址(无KYT对象)/无对手所(无TR对象)/账本内互换;大额门亦不设(2026-06评估)
  ─L3(旁路)─ 成交事件(带from/to币种+额)推TM → 命中 → 冻客户/冻余额 + case挂单
```
- **L1 跑在"确认成交"时点**（非报价点）——报价 30s 内客户可能被冻，成交须重判 L1。
- **「无 L2」是决策不是漏洞**：订单详情页 L2 栏显式展示"不适用（内部账本互换，无外部资金移动）"，防后人当缺陷。
- **L3 对兑换最重**：兑换是洗钱"离析"核心工具（脏 USDT→干净 AED），无 L2 的监控盲区全压 L3。
- **兑换无"未终态窗口"**（秒级完成）；但钱 100% 在账本内，L3 命中后**最好处置**（余额随时冻得住）。

### 4.4 三种单对照速查

| | 充值 | 提现 | 兑换 |
|---|---|---|---|
| L1 | 分流器（FROZEN/放行），**先跑** | 真门（单不建），订单上回显 | 真门，订单上回显，跑在成交点 |
| L2 | KYT(来源)+TR+人名核对 | KYT(去向)+TR+**大额审批门** | **无**（显式"不适用"） |
| L3 | 覆盖 | 覆盖 | **必须覆盖**（无 L2 补偿） |
| 订单前拦截 | ❌（钱已到） | ✅ | ✅ |
| 事中冻结金额 | ✅ 中转账户白送 | 锁余额（创建时） | ❌（秒级完成） |
| L3 命中处置 | 未终态置审查 / 已终态冻钱冻人 | 主要管人 + 后续挂起 + 上报 | 冻余额/客户（钱全在，最好管） |

## 5. 处置模型（订单侧 vs 人/钱侧）

### 5.1 两条处置路径 + 终态铁律

| 触发层 | 对象未终态 | 对象已终态 |
|---|---|---|
| L1/L2（闸门） | 改**订单**状态（FROZEN / ACTION_PENDING / REJECTED），走现有状态机 | —（闸门在终态前，不涉及） |
| L3（行为监测） | 可置订单为审查态（仅未终态） | **不碰订单**，动**人/钱**（冻客户 / 冻余额），case 挂订单作证据 |

**终态不可逆铁律**：已 SUCCESS 的订单**绝不拉回审查态**（违反平台记账铁律：历史不改、纠错走补偿，否则污染对账/审计/客户流水）。已终态命中 → 板子打在人/钱，订单只作证据链。

**竞态规则（必须写死）**：L3 说"置审查"的同一刻订单可能正推进终态。规则：**置审查只对未终态生效；抢输（单已终态）自动落到"处置人/钱"路径**，不许回拉。

### 5.2 record / case 数据模型（L3 核心）

| 概念 | 是什么 | 板子打在 |
|---|---|---|
| **record** | 行为引擎每次运行的留痕（哪个 trigger、扫了什么、命中没命中），无论命不命中都留 | 运行本身 |
| **case** | 命中后创建的处置单，独立状态机（OPEN→调查→RESOLVED/上报），SLA 升级 | **人 / 钱**（涉案客户/金额） |

- **case 双向桥**：case 挂**涉案订单列表**（上报 STR 时监管要交易明细）；L1/L2 的订单处置也可级联到人（制裁命中→单冻+人冻）。
- 与既有 V8 对账的 Run/Case 模式**同构**（团队零学习成本）。
- 心智模型与 V2「客户冻结」工作流对接：L3 case 的"冻客户"出口 = 复用 V2 冻结流。

### 5.3 L3 触发（trigger）

- **按订单粒度触发，绝不按资金单**——L3 分析"人做了什么"（订单=客户动作）；资金单是钱的执行细节（提现=1 payout+1 fee、兑换=4 腿），按资金单会重复计数、且混入内部归集/EOD 结算等非客户行为噪音。
- **双事件都推**：① 订单**创建**（attempted，"反复下单/被拒还试"是强信号）；② 订单**终态**（completed/failed，金额统计用真正落地的）。
- **四种 trigger 源**：交易发生（实时）/ 定时批扫（拆单看多天聚合，日终跑）/ Sumsub 告警 webhook（TM 主动推）/ 人工触发（MLRO 手动扫某客户）。
- **第一期"引擎"= Sumsub 告警承接层**（webhook→record→case），不自建规则/模型；txHash/成交数据的事后归档是 TM 的输入上游（见 §1 命名注）。

## 11. 附录 A · L2 集成契约（Sumsub KYT/TR，充值方向）

> 把 §4.2 充值 L2 的"用 Sumsub、挂单等回执"展开到接口级，供实现者照做。2026-07-12 brainstorm 追加。

### A.1 应然 L2 四步：规划 → 分发 → 收敛 → 裁决

| 步 | 做什么 | 等什么 | 铁律 |
|---|---|---|---|
| ① 规划 | 本地算这单的筛查清单（crypto: KYT必 + TR按三条件；fiat: 行为规则 + 人名核对，TR 恒 NOT_REQUIRED），每道一个独立状态字段初始 PENDING | 不等（毫秒） | **"不适用"也落库 + 带原因**（规划本身即证据） |
| ② 分发 | 清单里每道适用筛查**一次性并行**提交给执行方 | 不等；同步调用失败进重试队列 | 并行非串行（总时长=最慢一道）；外部服务挂**不得堵死入账管道** |
| ③ 收敛 | 每道各自等回执，独立 PENDING→PASSED/FAILED；某道转人工不作废其余 | KYT 秒级 / TR 分钟~天 / 人名核对等运营 | **每道必有超时出口**（无限等 = 钱悬在中转账户） |
| ④ 裁决 | 全部到终态触发：全 PASS/NOT_REQUIRED→放行入账；任一命中→FROZEN 转 MLRO | 等 ③ 全收敛（裁决本身毫秒） | **幂等**：由"最后一道回执到达"触发、非轮询；webhook 重推不二次记账 |

### A.2 同步响应 vs webhook（写死的铁律）

**状态字段（`kytStatus` / `travelRuleStatus`）唯一写入口 = webhook 处理器；同步响应绝不写状态。**

同步响应只做三件：① 确认提交成功（4xx/超时 → 重试队列，订单状态不动）；② 初评作**证据快照**落审计；③ 校验 txnId 对号。

四条理由：单一写入者（幂等只做一处）｜ 结论会翻案（on-hold→Reviewed 改判必须听 webhook）｜ 同步响应不可靠（超时/重试残缺，webhook 可重推）｜ 充值挂起型不差秒（客户无交互在等）。**唯一例外**：登录 ATO 等"必须在请求-响应周期内当场决定"的场景才直接用同步响应；充值/提现一律等 webhook。

### A.3 KYT 两种方式（pre-tx / post-tx）——充值为何单步

- **pre-tx**（送出前筛**目标地址**）：**提现独有**（主动送钱，送前得看对方地址干不干净）。
- **post-tx**（拿真实 txHash 筛**真实链上交易**）：两者都有。
- **充值**：钱到手时**已在链上**、天生有 txHash → 无"事前"（交易已发生）→ **只有 post-tx，单步**（代码 `applyKytResult`）。提现才 pre+post 两步（`kyt-phase1/2` + `archivePostKyt`）。此不对称由物理时序决定，非设计缺陷。

### A.4 KYT 掰开（充值）

1. **提交**：`POST /resources/applicants/{applicantId}/kyt/txns/-/data`，`type: finance`，带 源地址 + 真实 txHash + 金额 + 币种 + 方向 in。**txnId 自铸（`depositNo` 派生）**——webhook 靠它认领，别让 Sumsub 生成再回找。
2. **同步响应**：走 A.2 三用途。
3. **webhook 终局**：`applicantKytTxnApproved`(GREEN)→PASSED ｜ `applicantKytTxnRejected`(RED)→FAILED→FROZEN ｜ `applicantKytOnHold`→FROZEN（Sumsub 人审）→后续 `applicantKytTxnReviewed` 改判。放行后如需 MLRO 人工：`POST /resources/kyt/txns/{txnId}/review/status/completed` `reviewAnswer:GREEN`。

### A.5 TR 掰开（充值=入站）——两场景

> ⛔ **修正（2026-07-14，业主否决"独立 TR 交换实体表"）**：本节原写的"独立预告入账登记 + 认领匹配引擎"已否决——**TR 不建本地独立表**。**Sumsub 存 TR 交换真身（system of record）**；我方只在充值/提现**订单字段**上镜像 `travelRuleStatus`/`sumsubTxnId`/`counterpartyVasp`/`failReason`。决策见 memory `tr-exchange-table-rejected`。

TR 是"和对方 VASP 的一场对话"，结果 100% 靠 webhook。入站两剧本：

**场景 A · 信息先行（对方先发 TR，后打款）——无状态自动应答，不建本地预告表**
1. TR 到达（`applicantKytOnHold`）→ 归属确认可**无状态自动应答**：客户充值地址已预注册到 Sumsub 绑 applicant → 自动确认归属（`POST /resources/kyt/txns/{txnId}/travelRuleOwnership`）+ 从 applicant 资料自动带 PII → Sumsub 交叉核验、**记在 Sumsub**。我方本地**不落预告表**，顶多记日志。
2. 钱到账、Deposit 诞生 → 走**场景 B 姿势**（订单为锚）；**先查 Sumsub 有没有这笔的已完成交换**（按地址/txHash），有就直接读结果、不重发（txHash 幂等），没有才发起。
3. 补真实 txHash → Sumsub 记录闭环。

**场景 B · 钱先到（你发起 TR 追问）——订单是锚，天然绑定**
- 订单先在，发起时**自铸 txnId（`depositNo` 派生）+ 带真实 txHash**，无认领问题。
- **方向修正**：受益人 = 你家客户、PII 在你手、不用问；你向对方追的是**发款人(originator)信息**；核验 = 拿对方声称的收款人比对你库里客户真实身份。
- **"通过"分两层**：Sumsub 核验层给匹配结论（match→Approved / 不匹配→`counterpartyMismatchedData`）；你自己的 L2 汇合裁决才是订单放行——两层别捏一起。
- 超时出口：**Confirmation Timeout**（等对方所 N 小时无果 → 按拒/转人工）——"钱已在手、TR 不过 = 持币悬案"的必备兜底。

### A.6 三条工程铁律（实现必踩）

1. **先落库再外调**：先写订单侧 TR 分发标记（`travelRuleStatus=PENDING` + 自铸 `sumsubTxnId`），再调 Sumsub——防 **webhook 先于同步响应到达**时找不到单而丢事件。（原"预告记录"随独立表否决，见 A.5 ⛔）
2. **幂等**：webhook 会重推，同一事件（按 txnId + 事件类型）到两次不得二次写状态 / 二次记账。
3. **txnId 自铸**（`depositNo` 派生）作全链关联键，贯穿 提交 / webhook / 对账。
