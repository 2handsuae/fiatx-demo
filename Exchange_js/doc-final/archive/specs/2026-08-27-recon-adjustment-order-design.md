## 1. 定位与边界线

**定位**：一张调账单 = 一条对账差异项 + 一笔账本分录。**让账本与真实一致的一次更正。**

**它不是订单**（`decisions.md` 2026-08-28 三层职责）：没有「意图与执行之间的时间差」——批准即落账，没有在途、没有会失败的执行阶段。故：

| | 有 |
|---|---|
| 订单层（意图） | ❌ 无 |
| 资金单（物理转账镜像） | ❌ 无 |
| 账本分录 | ✅ **只有这一层** |
| 真实转账 | ❌ 无 |

**铁律⑤「钱动必过账」在本期不适用**——它管的是有在途要追的资金移动，纠错没有资金移动。

**边界线（最硬一条，代码与文档双处写死）**：

> **调账单不得用于补记真实发生的客户资金流入或流出。**
> 外面真有钱进出而我方未记的 → 走对应业务域把流程补跑起来。

## 2. 全路径一图流

```
对账跑批 → 钱包落 BREAK / SOFT_FLAG → 开 case → 差异项逐条列出
                                                      │
                    运营在 case 详情页点某条差异项 ────┘
                                                      ▼
                                        开调账单（选成因 + 方向 + 金额 + 两版原因）
                                                      ▼
                                   提交 → 审批中心（actionType=RECON_ADJUSTMENT_POST）
                                                      ▼
                          审批人屏幕看到的是后果本身，不是单号：
                          「本单将使客户 C0042 余额减少 15.00 AED，成因：重复入账，理由：…」
                                          ┌───────────┴───────────┐
                                       批准                      驳回
                                          ▼                       ▼
                  落账（账本分录，走 AccountingService，见 §3）    单据终态 REJECTED
                                          ▼
                       运营点 case 页现成的「重对账」按钮
                                          ▼
                       差额归零 → case 自愈 RESOLVED（机器关，人不点）
```

**形状与推单同构**——「操作员发起 → 不直写账本 → 落账 → 重对账 → case 自愈」。第 5 步那个按钮是推单时代做好的（`ReconciliationCasesDetailPage` 的 `handleReReconcile`），**直接复用，零新增**。

## 3. 分录：四种组合，成因不参与计算

现有 9 码科目，**本期不新增任何科目**。

| 账簿 | 方向 | 借 | 贷 |
|---|---|---|---|
| `CLIENT` | `REDUCE` | `CLIENT_PAYABLE` | `CLIENT_ASSET` |
| `CLIENT` | `INCREASE` | `CLIENT_ASSET` | `CLIENT_PAYABLE` |
| `FIRM` | `REDUCE` | `FIRM_OPS` | `FIRM_ASSET` |
| `FIRM` | `INCREASE` | `FIRM_ASSET` | `INCOME_OTHER` |

- **账簿**取自 case 的 `book`，不是表单字段
- **方向**指内部余额该往哪边动（对账量客户钱包用「客户应付 + 暂扣」，量公司钱包用公司权益各码）
- **成因一律不影响分录**——只用于留痕、客户文案、闸门

### 3.1 落账通道（由代码事实定死）

**不建资金单**：`FundsOrderService.create` 硬要求必须挂一张充值/提现/兑换父单，调账单挂不上；且本期无物理转账、无在途，资金单对它功能为零。

**走 `AccountingService.executeTransfer`**：既有过账入口，充值域的 `DEPOSIT_SUSPENSE_TO_PAYABLE`（`deposit-workflow.service.ts:1820`）就是一笔纯账面重分类，走的正是这条。**调账单一律不直写 TigerBeetle**（铁律③）。

**落账必带**：
- `debitWalletRef` / `creditWalletRef` = 该 case 的 `walletRef` —— 漏了则流水落不到出问题的钱包，delta 不归零、case 无法自愈。**本 spec 最容易写错的一处**
- `isExternalCrossing: false` —— 调账不出现在任何外部账单上。余额层汇总**全部** POSTED 流水（不按此字段过滤）故 delta 会缩小；明细层**只**拿 `true` 的去配外部行（`wallet-flow-matcher.service.ts:34` 注释：internal reclasses 排除），故不会造出新的孤儿行
- `effectiveDate` —— 业务生效日，`EvidenceParams` 现成字段（推单回填口）

## 4. 守卫：客户账簿加钱，必须有关联原单

> **`book=CLIENT` 且 `direction=INCREASE` 时，`relatedOrderNo` 必填且必须指向一张已存在的充值/提现/兑换单。**

判据的道理：

| 场景 | 有原单 | 判定 |
|---|---|---|
| 充值金额记少了 | ✅ 充值单 | 放行——KYT 已对这笔跑过，改金额不算绕闸 |
| 提现扣多了 / 撤销未冲 | ✅ 提现单 | 放行——钱本来就该还给客户 |
| 凭空多出来的钱（未归属入金） | ❌ | **拒**，走 V4 充值域补录 |

一条规则同时守住 §1 边界线与全部合法场景。

## 5. 成因清单（业主 2026-08-28 确认）

**客户账簿**（会改客户余额）

| 成因码 | 方向 | 客户口径词 |
|---|---|---|
| `DEPOSIT_AMOUNT_CORRECTION` | 加 / 减 | 充值金额更正 |
| `DEPOSIT_DUPLICATE_REVERSAL` | 减 | 重复入账撤销 |
| `DEPOSIT_SIGNAL_VOID` | 减 | 充值撤销（链重组 / 交易失败）|
| `WITHDRAW_AMOUNT_CORRECTION` | 加 | 提现金额更正 |
| `WITHDRAW_VOID_REFUND` | 加 | 提现撤销退回 |

**公司账簿**（客户完全看不到）

| 成因码 | 方向 | 说明 |
|---|---|---|
| `BANK_INTEREST` | 加 | 银行利息，归公司、客户不计息（`decisions.md` 2026-08-28）|
| `BANK_CHARGE` | 减 | 账管费 / 电汇费，公司承担（同上）|

**无兜底档**（§0 问题 12）。成因码与账簿、方向的合法组合在代码里写死，选不出非法组合。

> **`ASSET_SHORTFALL_ABSORB`（资产短缺认损，C3 第一步）一期不开放**，见 §0 问题 11。

## 6. 单据与状态机

### 6.1 粒度：一张单 = 一条差异项，不打包

一个 case 有 5 条差异项就开 5 张单。理由：客户可见性要求逐笔能对上（打包后客户流水出现一笔汇总「账务更正 −350」，对不上）；审批人也必须能逐条核；演示场景下差异项数量很小，省事的收益不存在。

### 6.2 字段

| 字段 | 说明 |
|---|---|
| `adjustmentNo` | 业务键，`ADJ` + YYMMDD + 序号。对外一律用它 |
| `caseNo` / `lineItemId` | 从哪条差异项开出来的 |
| `walletRef` | 取自 case，落账时必须带上（§3.1）|
| `book` | `CLIENT` / `FIRM`，取自 case，非表单字段 |
| `direction` | `REDUCE` / `INCREASE` |
| `reasonCode` | §5 七个成因码之一 |
| `relatedOrderNo` | 关联原单业务号；`CLIENT`+`INCREASE` 时必填（§4）|
| `assetCode` / `amount` | 金额按最小单位（分）整数 |
| `effectiveDate` | 业务生效日（可能不是今天）|
| `reasonInternal` / `reasonCustomer` | 两版文案：内部进审计，客户版留给读模型任务用 |
| `status` | 见 6.3 |
| `ownerNo` / `ownerId` | 客户业务号（对外）/ 客户 UUID（仅内部，落账要 `ownerUuid`，任何界面不得展示）|
| `approvalNo` / 提交人 / 审批人 / 各自时间 | 走审批中心，自动具备 |
| `tbTransferId` / `postedAt` | 落账留痕 |

### 6.3 状态机（4 态，2 终态）

```
DRAFT ──submit──► PENDING_APPROVAL ──approve──► POSTED    （终态）
                                   ──reject───► REJECTED  （终态）
```

- **`POSTED` 不可撤销**。账本只进不出。
- **开错了**：再开一张**反向的**调账单，把开错那张作为新单的「关联原单」。错误也是历史的一部分。
- 迁移表显式声明，非法跃迁显式拒绝（铁律④）。

## 7. 审批 · 权限 · 审计

**审批（复用，不自建）**：`ApprovalsService.createAndSubmit`，新增 handler 继承 `ApprovalHandlerBase`；`actionType = RECON_ADJUSTMENT_POST`，`workflowType = RECON`；默认策略**单步 `OPS_OFFICER`**（与现有运营类动作同形）。批准事件回调才落账，**批准与落账之间不得有第二个人工环节**。

审批页必须把后果直白展开成一句人话（§2 图中示例），而不是「批准调账单 ADJ…」。**审批看不见后果，就是橡皮图章。**

分级审批 / 新增 `CFO` 角色**不做**（应然设计写明 v1 可扁平；策略表本就可配）。

**权限（maker 侧）**：新增 `RECON_ADJUSTMENT_WRITE`（开单）；读面复用 `RECON_CASE_READ`。登记进 `rbac.catalog.ts` + `db:base:sync` + **重启后端**。

**审计（对账域 4 → 5 码）**：

| 码 | 模式 | 硬字段 | 说明 |
|---|---|---|---|
| `RECON_ADJUSTMENT_POSTED` | **INHERIT**（继承关联原单旅程）| `reasonCode`, `direction`, `amount`, `effectiveDate` | 主对象 = `adjustmentNo`；OWNER = 客户号；RELATED = caseNo。与 `RECON_PUSH_ORDER` 同为「落在别人旅程里」的对账件 |

提交 / 批准 / 驳回由审批中心自行留痕，域内不重复造词。

## 8. 收口：重对账与 case 自愈

- 落账后由运营点 case 详情页**现成的「重对账」按钮**触发；**调账单本身不碰对账引擎**（同推单结论：每处置必跑会造成大量白跑与快照噪音）
- 重跑后差额归零 → 现有 `autoHealCases()` 置 `RESOLVED` + `resolutionReason='AUTO_HEALED'`
- **不新增 `MANUAL_RESOLVED` / `WAIVED` 写方**：处置全部落账，case 一律走自愈关闭

## 9. 验收标准（实现期展开为 plan 硬闸）

1. 四道 tsc 全绿；本域 jest 净新失败 0
2. **行为断言，非文本扫描**：开单 → 审批 → 落账 → 重对账 → case 转 `RESOLVED` 全链 e2e，覆盖客户账簿减、客户账簿加（带原单）、公司账簿加三例
3. `verify:coa` 两条恒等式在**四种分录组合各自落账后**仍全绿，且无负余额
4. 审批未通过时**不得**产生任何账本分录（反向断言）
5. `POSTED` 状态下再次提交/驳回被状态机显式拒绝
6. `CLIENT` + `INCREASE` 且无 `relatedOrderNo` 被显式拒（§4 边界线）
7. 非法「成因 × 账簿 × 方向」组合被显式拒（§5）
8. 前端改动须起 preview 渲染 + 截图验证（tsc 通过不算数）

## 附录 A · 客户钱包差异场景全枚举（源头推导，2026-08-28）

差异只可能来自四种原子成因：真有钱进来我方没记 / 我方记了钱出去但没出去 / 我方记了钱进来但没进来 / 真有钱出去我方没记。

**外多内少**

| # | 场景 | 客户真损失 | 出路 |
|---|---|---|---|
| A1 | 打了钱，监听漏了，完全没建单 | 是 | V4 补录（BACKLOG）|
| A2 | 充值单在，金额记少了 | 是 | **本期 · 充值金额更正** |
| A3 | 认不到主人的入金 | — | V4 待认领（BACKLOG）|
| A4 | 银行付息到客户 vIBAN | 否 | 不建模（利息归公司，按月从公司账户结算）|
| A5 | 客户重复打款，只记一笔 | 是 | V4 补录（BACKLOG）|
| D1 | 提现记账但转账失败/退回，回调漏了 | 否 | 提现域 `onBounce`（BACKLOG 已有）|
| D2 | 提现扣多了 | 是 | **本期 · 提现金额更正** |
| D3 | 提现已撤销但账没冲 | 否 | **本期 · 提现撤销退回** |

**外少内多**

| # | 场景 | 客户真损失 | 出路 |
|---|---|---|---|
| B1 | 中转行扣费致实到少于申报 | — | **不存在**：手续费按月从公司账户收，客户无感（`decisions.md` 2026-08-28）|
| B2 | 精度 / 单位记多了 | 否 | **本期 · 充值金额更正** |
| B3 | 假充值信号（链重组 / 交易失败）| 否 | **本期 · 充值撤销** |
| B4 | 同一笔充值记了两次 | 否 | **本期 · 重复入账撤销** |
| C1 | 银行从客户账户扣账管费 | — | **不存在**：同 B1 |
| C2 | 提现真付出去了，我方没记 | 否 | 提现域补跑 |
| C3 | **未授权转出**（钥匙泄露 / 内部人作案 / 银行误划）| **是，且不该他承担** | 认损（二期一起开）+ 补款（二期）+ 事故登记（三期）|

**公司钱包侧**：银行利息（→ `BANK_INTEREST`）、账管费/电汇费（→ `BANK_CHARGE`）—— 演示破口场景 5「银行杂费」与 7「银行利息」正是这两个。
