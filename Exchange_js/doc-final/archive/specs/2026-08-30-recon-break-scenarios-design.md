# 对账破口场景按成因铺全（recon:demo:break 重做）

> 状态：设计定稿，待写实施计划
> 日期：2026-08-30
> 相关：`2026-08-29-recon-disposition-actions-design.md`（处置动作收口，排在本轮之后）

---

## §0 为什么要做这一轮

现在 `recon:demo:break` 造 9 个场景。业主要求**按成因把现实里会发生的破口铺全**，理由是顺序问题：

> 破口是**现实的样子**，跟解法无关。先把现实铺全，解法一个个补。

反过来——先做解法再造场景——会让**场景去迁就按钮**。上一轮 spec 里加「重复入账」的理由白纸黑字写着"冲销没有干净的演示位"，那就是**用按钮反推现实**，跟本仓库栽过多次的自证型绿灯是同一个毛病：让被测对象决定测试内容。

### §0.1 讨论中确立的口径（结论，不要翻案）

| 结论 | 依据 |
|---|---|
| **形状是封闭的（4 类），成因是开放的** | 引擎只认「金额不对 / 我有外无 / 外有我无 / 在途」；成因是人判断的，本 spec 铺 15 条 |
| **同形 + 不同出口 = 教学点；同形 + 同出口 = 冗余** | 判据本身成立，但我最初用它砍掉 ⑩⑪ 是**算错了**——「对方金额记错」与「我方小数点错位」形状相同、**出口相反**（一个冲正、一个不该动账）。三族各自都有「我方错 / 对方错 / 都没错」三真相结构，15 条全都有位置 |
| **一个钱包可以挂多条差异** | 业主拍板，现实本来如此。代价是必须显式废除生成器的 disjoint-wallet 前提 |
| **展示位：每屏一个形状、多种真相** | 同一个形状三条差异、三种相反处置摆在一屏，是整套演示最值钱的一屏 |
| **花名册"每种状态都要有样本"是覆盖下限，不是每种只能一条** | 业主澄清。故为对账素材增加订单不违反花名册原则 |
| **不做：归属（未归属外部账户）** | 业主拍板退役。⚠️ 只删种子注入，**引擎的 `unattributedBalances` 分支与其单测保留** |
| **不做：`HELD`（对账单没到）** | 业主拍板，以后做。引擎没有这个桶，案子根本开不出来，本轮造不了 |
| **不做：豁免 / 挂起** | 上一轮已定。故「不该动账」那几条今天落在"无出口"上，这是诚实的现状 |

## §2 生成器现有机制（本轮建立在它之上）

两段式，**账本一次都不碰**（这是它能反复跑的原因）：

1. **镜像**（`planWallets` + `writeMirror`）：每个钱包的内部 `isExternalCrossing` 流水逐笔镜像成外部对账单行；外部收盘 = 内部余额。期初 0 + Σ(IN−OUT) = 内部净额，**天生完美对上**
2. **注入**：只在外部这一侧制造扭曲

四个杠杆：

| 杠杆 | 造出什么 |
|---|---|
| 删一条外部行 + 压低收盘 | 我有外无 |
| 加一条幽灵外部行 + 抬高收盘 | 外有我无 |
| 改一条外部行的金额 + 调收盘 | 金额不对 |
| 留一笔真的非终态资金单 | 在途 |

**新增第五个杠杆**：挪一条外部行的时间到截止点之后（`fetchExternalLinesForWallet` 按 `datetime <= cutoff` 取行），**收盘不动** → 余额平、流水配不上 → `SOFT_FLAG`。

**15 条里只有「我方重复入账」需要写账本**：要让"重复"在屏幕上看得出来，得有两笔同 externalRef 的内部流水，而 owned 科目上天然不存在同 ref 的两笔（实测：同 ref 的多行都是同一笔转账的借贷两腿，其中聚合腿被匹配器丢弃）。

## §3 成因表：三族 × 三真相

| 形状 | 我方错 | 对方错 | 都没错 |
|---|---|---|---|
| **金额不对** | ④ 小数点错位 → **冲正** | ⑩ 对方金额记错 → **不该动账** | ⑪ 舍入精度差 → **不该动账**（该豁免） |
| **我有外无** | ⑦ 重复入账 · ⑧ 假信号入账 → **冲销** | ③ 银行漏报明细 → **不该动账** | ⑫ 跨日切 → **等下期** |
| **外有我无** | ⑤ 漏监听充值 → **走充值域** | ⑨ 对账单重复行 → **找银行** | ⑥ 退汇 → 看情况 |
| **在途** | — | — | ① 在途时序差 → **去推单** |
| **公司侧补记** | — | ⑭ 银行杂费 · ⑮ 银行利息 → **补记** | — |
| **跨钱包** | ⑬ 记错钱包 → 两边各自 | — | — |
| **净额口径差** | — | ② 手续费轧差 → **冲正** | — |

15 条。「不该动账 / 走充值域 / 找银行 / 等下期」今天都落在**无出口**上——豁免与挂起没做，这是现状，不粉饰。

## §5 逐场景规格

### §5.1 展示位甲 · Grace AED —— 同样是「金额不对」

| # | 成因 | 谁错了 | 杠杆 | 出口 |
|---|---|---|---|---|
| ④ | 小数点错位 | 我方 | 改一条行的金额（×100） | **冲正** |
| ⑩ | 对方金额记错 | 对方 | 改另一条行的金额 | 无出口（该找银行） |
| ⑪ | 舍入精度差 | 都没错 | 改第三条行（极小额） | 无出口（该豁免） |

### §5.2 展示位乙 · Frank AED —— 同样是「我有外无」

| # | 成因 | 谁错了 | 杠杆 | 出口 |
|---|---|---|---|---|
| ③ | 银行漏报明细 | 对方 | 删一条行 + 压收盘 | 无出口（我方账是对的） |
| ⑦ | 我方重复入账 | 我方 | **账本写第二笔同 externalRef 的充值** | **冲销** |
| ⑧ | 假信号入账 | 我方 | 删另一条行 + 压收盘 | **冲销** |

期望桶 **BREAK**。

⑦ 的**可辨识证据**：银行只报了一笔、我方入了两笔 → 匹配器 Pass 1 按 ref 配对，一笔匹配上、另一笔成孤儿，**两行同 ref 同额**。屏幕上"这条孤儿在已匹配列表里有个同号双胞胎"就是重复的铁证；③⑧ 的孤儿没有双胞胎。**这是整份 spec 里最值钱的一个对照。**

⑦ 的账本写入用**固定 sourceNo**（`DEMO-DUP-<业务日>-<钱包前8位>`）保证可重跑：TB 的 transfer id 是 (sourceType, sourceNo, eventCode) 的确定性哈希，重跑时判为已存在直接跳过。⚠️ `recon:demo:reset` **不回滚账本**（它只清外部数据与 WALLET_V1 的 run/case），彻底归零要走 `stack.sh reset self`。

### §6.1 硬规则：素材订单一律不加提现

提现会留下手续费腿；一旦某笔没走到终态，那个钱包就带上了非终态资金单，在途识别会去认领它，把场景的期望桶打乱。这正是 `cfec505f` 修的坑（花名册 #20 的费腿撞了公司手续费户，9/9 掉成 7/9）。

**新加的素材单一律走能干净结清的域（充值、兑换）。**

## §7 断言模型：拆成两级

现状每个场景带一个 `expectedBucket`；一钱包多场景之后这个值没有意义——**桶是钱包的属性，不是场景的**。

```ts
/** 每个场景断言：我造出了哪一条差异行 */
interface ScenarioExpectation {
  scenarioId: number;
  rootCause: RootCause;
  walletRef: string;
  expectedLineType: 'IN_TRANSIT' | 'AMOUNT_MISMATCH' | 'ORPHAN_INTERNAL' | 'ORPHAN_EXTERNAL';
  amount: string;
  externalRef: string | null;
  detail: Record<string, unknown>;
}

/** 每个被注入的钱包断言：它最终落在哪个桶 */
interface WalletExpectation {
  walletRef: string;
  scenarioIds: number[];
  expectedBucket: 'IN_TRANSIT' | 'SOFT_FLAG' | 'BREAK';
  /** 多场景钱包必填：桶是怎么推出来的，供审的人核 —— 见 §9 风险 */
  bucketRationale: string;
  /** claude-43 的 B 轴显式输入，见 §8 */
  hasNonTerminalFundsOrder: boolean;
}
```

判据从两条变三条：

1. **按场景** —— 每条场景在它的钱包上产生了期望类型的差异行
2. **按钱包** —— 每个被注入的钱包落在期望的桶
3. **两条自洽式原样不动**：
   ```
   identity①  walletCount == matched + inTransit + softFlag + break
   identity②  opened + reObserved == inTransit + softFlag + break
   ```

### §7.1 自洽式为什么不用改

`wallet-recon-run.service.ts:402`：`walletsChecked = walletRefs.length + unattributedBalances.length`。

退役未归属账户 → `unattributedBalances` −1；新增钱包并写外部余额头 → `walletRefs` +N。两侧同增同减，桶计数同理。**这两条式子在场景增删时应当纹丝不动；任何"需要改它才成立"的时刻，本身就是警报。**

## §8 注入前的前置闸（fail-closed）

除了在途场景那个钱包，**其余每个目标钱包必须没有非终态资金单**；有就直接报错，说明业务数据变了、场景分配要重排。

出处与理由（claude-43，`cfec505f`）：这条防的**不是场景之间撞车**，是**业务数据污染场景**——两个独立的轴。一个钱包上有 `demo:all` 留下的非终态资金单，引擎会（正确地）产生 IN_TRANSIT 行并把桶重判成 BREAK，而答案键期望 SOFT_FLAG。

**必须是显式报错，不许静默降级。** 他的原话：

> 这轮最难查的不是 bug 本身，是它静默——`demo:all` 全绿、`recon` 报 7/9，中间没有任何东西说"我挑钱包时妥协了"。

## §9 已知风险

1. **多场景钱包的期望桶是人算出来的**。算错了就是答案键错，而答案键错的表现是**测试绿着但证明了错的东西**。单场景钱包没这问题（一个场景一个桶，一眼可查），三个展示位是本轮新引入的风险面。
   **对策**：`WalletExpectation.bucketRationale` 必填，写清推导（如"三条同向金额差之和 ≠ 0 → BREAK"），让审的人能核，而不是只看到一个结论。这不消灭风险，但让它可审。

2. **⑦ 是唯一写账本的注入**，其余 14 条纯外部。它用固定 sourceNo 保证幂等，但 `recon:demo:reset` 不回滚账本——彻底归零要 `stack.sh reset self`。

3. **本轮显式废除生成器的 disjoint-wallet 前提**（`recon-demo.ts` 文件头写着"Each scenario targets its own wallet … so cases stay disjoint and per-scenario checks are independent"）。文件头注释必须同步改写，否则下一个人会照着一句已经不成立的话做判断——这正是本分支上 C_CMA 那两句注释骗人的同款毛病。

4. **「不该动账」那几条，收口之后不是没按钮，而是按钮对它们是错的**——这条比"没出口"严重，我第一版写错了。按下一轮收口的判定表逐条对：

   | 场景 | 收口后显示什么 | 真相 | 后果 |
   |---|---|---|---|
   | ⑤ 漏监听充值 · ⑨ 对账单重复行 · ⑥ 退汇 | **无出口**（客户侧外有我无） | 各不相同 | 安全——点不了 |
   | ⑩ 对方金额记错 · ⑪ 舍入精度差 | **冲正**按钮 | 我方账是对的 | ⚠️ 点下去把对的账改错 |
   | ③ 银行漏报 · ⑫ 跨日切 | **冲销**按钮 | 我方账是对的 | ⚠️ 同上 |

   也就是说：**只有 3 条是"点不了"，另外 4 条是"点得了但会做错事"，而且差额会归零、案子会关掉、报表上一片干净——没人会发现。** 这正是收口 spec §8 短板 3 记的那条（"按钮仍可能被点错，本轮靠必填的内部原因兜，根治要等挂起与豁免"）。

   本轮把这 4 条铺出来，等于**把那个缺口摆到台面上**——这是好事（缺口可见比缺口隐形强），但走查时必须讲清楚，否则演示者自己会照着按钮点错。豁免与挂起做完之前，这 4 条的正确演法是"指出来、不点"。
