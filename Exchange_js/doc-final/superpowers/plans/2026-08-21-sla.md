# 三域 SLA 收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让三个交易域的 SLA 变成「进某个状态就开始计时，时间到了按规则处置」，并且能在演示现场当场触发。

**Architecture:** 三域统一用 `slaDeadline` 列计时（兑换补列），deadline 在各域状态机的**收口处**（`updateStatus` / `markStatus`）按目标状态统一设，而不是逐个调用点挂钩。破线分两类：硬 SLA 推状态，软 SLA 只置 `slaBreached` 标记。管理台列表页/详情页显示剩余时间与红标，详情页 action 栏提供「模拟超时」按钮。

**Tech Stack:** NestJS 10 · Prisma 5 (SQLite) · TypeScript · Jest · React (admin-web)

**Spec:** `doc-final/superpowers/specs/2026-08-21-sla-design.md`

## Global Constraints

以下约束对**每一个** Task 都生效，不再逐条重复：

- **Demo 数据约定**：数据可随时格式化重铺（`npm run main:reset:biz`）。**禁止**为旧数据写 backfill、迁移兼容层、双写过渡或向后兼容列。schema 改动直接按目标终态做。唯一例外：`prisma/migrations` 仍按正常流程新增（保证空库能从零建起），但迁移内容不必兼容已有行。
- **铁律 ①**：有持久状态、operator 可见的操作 → **必须**写 `AuditLogsService`（DI 注入，禁止 `new`）。
- **铁律 ②**：多表状态变更 → **必须**用 DB transaction。
- **铁律 ③**：有稳定业务键（`depositNo` / `withdrawNo` / `swapNo`）→ **禁止**以 `id` 作主查询合同。
- **铁律 ⑤**：Workflow **禁止**直接写 domain 实体的 Prisma 表 → 必须通过该 domain 的 service 方法。
- **deliberate fork**：三个交易域是**故意分叉**的（仓库 29 处成文记录），**禁止**为本轮改动抽公共基类、公共常量或泛型工具。同样的修改在三个域各写一遍。
- **tipping-off 铁律**：`slaDeadline` / `slaBreached` **绝不能进客户面响应**。客户面白名单已经排除了它们（`deposit-transactions.service.ts:265-275` 的注释明写这是 tipping-off guard）——**不要动那个白名单**。
- **验证盲区**：本项目 `tsconfig.json` 只 include `src/**/*`、`jest.config.js` 的 `roots` 不含 `test/`。改了跨 src/test 边界的类型后必须加跑 `npx tsc --noEmit -p tsconfig.test.json`。全量 `npx jest` **不能带路径过滤**（roots 含 `admin-web/src` / `client-web/src`，带过滤会照不到）。
- **每个 Task 结束必须 commit**，message 用中文，格式 `<type>(<scope>): <说明>`。

## ⚠️ 一个会咬人的交互（所有 Task 都要知道）

硬 SLA 破线时，现有代码传 `extraData: { slaBreached: true }`（`deposit-sla.service.ts:62`、提现同构）。

本批把 deadline 改到状态机收口处统一设之后，**进入新状态会重设 deadline 并把 `slaBreached` 归 `false`**。两者一撞：

```
硬破线 → updateStatus(SLA_BREACH) → 进 MANUAL_CHECKING
  收口处设新的软计时（3 天）+ slaBreached=false
  ...然后 extraData 的 { slaBreached: true } 覆盖回 true
  → 新的软计时器一出生就被标成「已破线」，永远扫不到
```

**处置：硬路径去掉 `extraData: { slaBreached: true }`。** 它原本的作用是「防重复扫」，而状态一变，旧候选就不再匹配 `slaDeadline < now`（新 deadline 在未来），天然不会重复处理。

软路径的 `slaBreached: true` **是**这次破线的全部动作（不推状态），走独立的 `markSlaBreached()`，不经 `updateStatus`。

- [ ] **Step 3: 充值加配置表 + 解析函数**

`src/modules/trading/deposit-transactions/deposit-transactions.service.ts`，在 `DEPOSIT_TERMINAL_STATUSES` 定义附近加：

```typescript
/**
 * 充值域 SLA 配置（2026-08-21 第三批）。key = 进入该状态后开始计时，value = 分钟数。
 * 不在表里的状态 = 不计时（终态、等外部执行的态、FROZEN）。
 *
 * ⚠️ SLA 按「状态」计时，与状态内部发生了什么无关。此前把计时挂在 onHold 回调上
 * 是错的挂法——没收到 onHold 的单永远不计时，那正是「Sumsub 不回、单子永远挂着」
 * 的成因。不要再把任何 SLA 逻辑绑到某个 webhook 上。
 */
const DEPOSIT_SLA_MINUTES_BY_STATUS: Partial<Record<DepositTransactionStatus, number>> = {
  [DepositTransactionStatus.COMPLIANCE_PENDING]: 5,            // 等 Sumsub 回裁决
  [DepositTransactionStatus.ACTION_PENDING]: 7 * 24 * 60,      // 等客户交材料
  [DepositTransactionStatus.MANUAL_CHECKING]: 3 * 24 * 60,     // 软:等合规官
  [DepositTransactionStatus.OPERATION_PENDING]: 1 * 24 * 60,   // 软:等运营
};

/**
 * 软 SLA：破线只置 slaBreached 标记、**不推状态**。
 * 业主裁定：超时的是我们自己人，不能把怠工转嫁给客户——单子该怎么判还得人判。
 */
export const DEPOSIT_SLA_SOFT_STATUSES: ReadonlySet<string> = new Set<string>([
  DepositTransactionStatus.MANUAL_CHECKING,
  DepositTransactionStatus.OPERATION_PENDING,
]);
```

在 `DepositTransactionsService` 类内加：

```typescript
  /**
   * 进入 nextStatus 时该带的 SLA 字段。有配置就起新计时，没配置就清空。
   * slaBreached 一律归 false —— 换了状态就是换了等待对象，旧的破线记录不该跟过来。
   */
  private resolveSlaFields(nextStatus: DepositTransactionStatus) {
    const minutes = DEPOSIT_SLA_MINUTES_BY_STATUS[nextStatus];
    return minutes === undefined
      ? { slaDeadline: null, slaBreached: false }
      : { slaDeadline: new Date(Date.now() + minutes * 60_000), slaBreached: false };
  }
```

```typescript
/**
 * SLA 剩余时间展示（2026-08-21 第三批）。
 *
 * 这是本批唯一放进公共 utils 的东西 —— 它是纯展示格式化，不含任何域业务逻辑。
 * 三域的 SLA **配置**（哪个状态计时、多久、超时去哪）仍各自留在各自的 service 里
 * （deliberate fork），不要把配置也搬过来"统一"。
 */
export type SlaTone = 'none' | 'normal' | 'breached';

export function formatSlaRemaining(
  slaDeadline: string | null | undefined,
  slaBreached: boolean | undefined,
): { text: string; tone: SlaTone } {
  if (slaBreached) return { text: '已超时', tone: 'breached' };
  if (!slaDeadline) return { text: '—', tone: 'none' };

  const ms = new Date(slaDeadline).getTime() - Date.now();
  if (ms <= 0) return { text: '已超时', tone: 'breached' };

  const totalMinutes = Math.floor(ms / 60_000);
  const days = Math.floor(totalMinutes / (24 * 60));
  const hours = Math.floor((totalMinutes % (24 * 60)) / 60);
  const minutes = totalMinutes % 60;

  if (days > 0) return { text: `${days}d ${hours}h`, tone: 'normal' };
  if (hours > 0) return { text: `${hours}h ${minutes}m`, tone: 'normal' };
  return { text: `${minutes}m`, tone: 'normal' };
}
```

> ⚠️ `slaBreached=true` 优先于时间计算：软 SLA 破线后状态不变、deadline 也不变，只有这个标记能表达"已经超时了"。
