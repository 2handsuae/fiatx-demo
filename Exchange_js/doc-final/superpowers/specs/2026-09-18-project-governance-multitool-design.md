# Skill 设计（第二轮）：project-governance 多工具扩展

2026-09-18 ｜ 状态：设计稿，业主已口头批准，待写 plan ｜ 首轮设计：`archive/superpowers/specs/2026-09-15-methodology-skill-design.md`

## 0. 本轮解决什么

首轮交付的 `project-governance` 只考虑单工具（Claude Code）。本轮扩展到**多工具串行接力**：同一个项目文件夹，Claude Code 与 Codex 都能读到同一份总纲、按同一套规矩干活。

业主本轮明确的三个目标与判定：

| 目标 | 现状 | 本轮要做 |
|---|---|---|
| ① 配合 superpowers | **已满足**，两侧都装了（Claude 6.1.1 ｜ Codex 6.3.0，清单同为 14 技能） | §6 补产物契约层——写 superpowers 不知道的项目特有要求 |
| ② 开局定骨架、逐轮长细节 | 机制已有（种子访谈＋回写泵四时机） | checklist 拆两类，补 7 行通用种子行，补上"回写泵在 plan 里没有落点"这一格 |
| ③ 多 agent 接手 | 无 | 入口文件双名、交接面一行路由；**并发隔离不做** |

## 1. 已核实的事实（本轮所有设计的地基）

- Claude Code **不读** `AGENTS.md`（官方 memory 文档原话：reads CLAUDE.md, not AGENTS.md）；提供 `@path` 导入与符号链接两条官方路径。
- Codex 读 `AGENTS.md`（全局 `~/.codex/AGENTS.md` 实存）。**项目级 `AGENTS.md` 是否被读，本轮须实证**（见 §7）。
- 两侧 superpowers 均可用：Claude 侧 `plugins/cache/claude-plugins-official/superpowers/6.1.1/`；Codex 侧 `plugins/cache/openai-curated-remote/superpowers/6.3.0/`（抽查 writing-plans/SKILL.md 可读）。
- `~/.codex/skills/` 下 9 个指向 `~/.codex/superpowers/` 的软链**全部悬空**（旧手工安装残留，已被插件安装取代）——工具债，本轮不修，登记即可。
- 插件缓存路径带版本号，升级即变——**跨工具共享 skill 的软链只能指向路径稳定的真身**（如 `~/.claude/skills/<name>`），不能指向插件缓存。

判例（两次犯在同一轮）：先断言"Codex 与 Claude 两侧都装了 superpowers"未验证指向；被业主质疑后只查 `~/.codex/skills/` 一个路径就反向断言"Codex 没有 superpowers"，仍错。**结论必须在它断言的那个位置复现，且否定性结论要搜遍所有可能安装位置。**

## 2. 入口文件：CLAUDE.md 真身 ＋ AGENTS.md 软链

```
项目根/
├── CLAUDE.md      ← 总纲真身（业主日常直接看它；Claude Code 原生读）
├── AGENTS.md      → 软链指向 CLAUDE.md（Codex 读它）
└── docs/          ← 中立，两个工具都读
```

**为什么软链而非 `@import`**：`@import` 要求 Claude 侧当壳、真身叫 AGENTS.md，而业主主力是 Claude Code、日常直接看总纲；且 Codex 是否支持导入语法未经验证。软链两边读到的是同一份字节，不依赖任何一方的导入机制，官方文档亦认可。限制"软链时不能加工具特有内容"对本设计不成立——派发分层按工具分行写在同一份里，无独立的工具特有内容。macOS 无 Windows 软链权限问题；业主机器 skills 目录早已大量使用软链。

**两个名字都必须登记进路由表**，否则违反总纲自己宣布的封闭性（与首轮终审逮到的 review-rubric 路由孤儿同类）。

## 3. §6 产物契约：两层写法

上层（项目特有、工具中立，任何工具照做）：

- 每个任务要有一份 spec 落 `docs/superpowers/specs/`、一份 plan 落 `plans/`
- **plan 必须引用 checklist 并圈定本任务触发哪几行**，收尾核对表写死进 plan
- 多波战役的每波 spec 必须带「承接上一波」节

下层（实现方式）：装了 superpowers 的工具走 `brainstorming` → `writing-plans` 产出它。

**为什么必须有上层**：这三条 superpowers 全不知道——它的 writing-plans 不知道本项目要求 plan 圈 checklist 行，brainstorming 不知道波 spec 要带承接节。这些是项目特有的产物要求，只能写在总纲。次要理由：两侧版本会漂移（6.1.1 vs 6.3.0），将来可能加入没有 superpowers 的工具。

## 4. delivery-checklist 拆两表

两类的**纪律不同**，故分两张表而非一张表加标记——纪律不同的东西混在一张表里，早晚纪律也混。

### 4.1 通用表（出厂自带，封闭）

判定口径：**换任何项目这条还成立吗？** 源项目 20 行中 7 行成立：

| 触发 | 必须做 | 漏了会怎样 |
|---|---|---|
| 新增用户可见能力 | 必须有可达入口 | 点不到＝这个功能不存在 |
| 退役能力 | 同步删入口 | 幽灵按钮：点得到、点了没反应 |
| 改了平行结构中的一个 | 问其余的一不一样 | 平行模块漂移是最大的缺口来源 |
| 改了肉眼可见的东西 | 渲染出来用眼睛看 | 类型检查与单测对渲染结果一无所知 |
| 改了持久数据结构 | 确认从零能建起来 | 别人拉了代码跑不动 |
| 本任务是多波中的一波 | 承接记录写进下一波 spec 开头 | 下一波重新论证走过的路 |
| 每轮收尾 | CHANGELOG 一行＋销账＋过回写泵三问 | 骨架不生长，放三个月还是空的 |

三、四两行的实证最强：源项目 BACKLOG 有 14 条源自「平行结构」那条，而「肉眼可见必看」是其两条永不豁免之一。

**纪律：出厂即封闭，项目里不许往通用表加行。** 想加＝回来改 skill 本身——那是跨项目的、有意识的决定，门槛远高于在某个项目里顺手加一行。这同时给了 skill 一条正当的生长通道。

### 4.2 项目表（空表起步）

纪律不变：**无事故不进表**，一行＝一次真实事故（日期＋现象＋代价）。

业主本轮裁定归入项目类的两条边界：「新增状态→顺带回答要不要计时」「新增需多处登记才生效的东西→列全登记点」——够通用但触发条件依赖项目结构，执行者扫左列时未必认得出自己撞上了它。

### 4.3 为什么破"空表起步"

通用表的行不是"连带遗漏"（动了 A 忘了 B，必须靠事故喂），而是**流程本身**，第一天就成立。尤其「每轮收尾」那条：回写泵写在总纲 §9，但 plan 圈行时表里没有这条就圈不到它——机制与执行之间断了一格，本轮正是补这一格。

## 5. 交接面：路由表加一行

新增行：**接手新一轮** → `modules/overview.md` → `decisions.md` → `CHANGELOG.md` 最近几条 → `BACKLOG.md`（选题）；有在途战役则读战役总纲＋承接记录。

**明确不做**：轮内（半途）交接面。业主的用法是一轮做完才换工具，token 不够也会把当前轮干完，不存在"干到一半 Codex 接手"。为它建设就是预防性建设。相应地不写"频繁提交即交接协议"——superpowers 的 plan 本就要求频繁提交。

## 6. 并发隔离：不做

业主明确串行、不并行。装了就是从来不红的闸门（纯成本）。§10 运维事实留一句路标即可：「本项目按串行接力使用；要并行请先定隔离约定（分支／worktree／端口／数据）」——一句话，不是机制。

## 8. 本仓实证（同轮执行，验证多工具路径真成立）

1. `Exchange_js/../CLAUDE.md`（仓库根）保持真身不动，同目录新增 `AGENTS.md` 软链
2. 总纲 §8 路由表补登记两个入口文件名
3. **实测**：在本仓起一个 Codex 会话，确认它读到了项目级 `AGENTS.md`（软链）的内容——这是本设计唯一未经验证的假设，红了则回退到 `@import` 方案并把真身改名

## 9. 验收标准

1. skill 改动后跑一次多工具开荒演练（模拟答卷含"Claude Code 和 Codex 都要干活"），产出应含 `CLAUDE.md` 真身＋`AGENTS.md` 软链、两张 checklist 表、路由表含入口文件与接手行
2. 单工具答卷演练一次，确认**不**生成 `AGENTS.md`（分路正确，不给单工具项目添无用文件）
3. 通用表 7 行逐行在产出物中可查；项目表为空表
4. 本仓 §8 实证通过（Codex 读到软链 AGENTS.md）
