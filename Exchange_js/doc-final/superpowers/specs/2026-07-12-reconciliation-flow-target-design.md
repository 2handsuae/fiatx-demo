# 对账流程 · 应然设计（标准 6 步 × 平台落地）

> **Status**: 设计稿（应然 / target design）。本文描述"对账**应该**怎么落地"——以平台整体设计思路 + 行业标准为准，**不以当前代码现状为准**。
> **当前代码现状**见 [`reference/truth/v8-recon.md`](../../reference/truth/v8-recon.md)；本文末 §8 给出「应然 vs 代码实际」差距。
> **Date**: 2026-07-12
> **来源**: 逐轮 brainstorming 收敛 + 三路行业调研（通用对账标准流程 / 差异分类与处置 / 加密托管对账 + VARA）。
> **范围**: 对账**检测** + **在途处置**闭环。真差异（BREAK）处置、VARA 合规（通报/留存）**显式留空**（见 §9）。

## 0. 背景与地基

### 0.1 定位

对账 = 每日把**内部账本**（TigerBeetle 记的"每客户每币种应有多少"）与**外部真实资金**（银行 / HexTrust 托管 / 链上余额）**逐个物理钱包 1:1 核平**，差异按性质分类、开案追踪、能自动平的自动平。它是资金安全与合规的最后一道核验闸。

监管锚点：VARA Custody Services Rulebook 要求持牌方**每日**对账、**逐客户钱包隔离**、出现**未纠正的重大差异须通报 VARA**、记录留存 **≥8 年**、至少每月出客户账单（III.B / III.D / C.Reconciliation）。

### 0.2 平台与对账整体思路（7 条，已确认）

1. **实时 1:1 镜像账本**——TigerBeetle 是余额唯一真相，每笔交易就地记账，`客户资产 ≡ 客户负债`（按币种）任何时刻恒等，无延迟结算 / EOD 轧差。
2. **一切围绕真实资金移动**——资金单（funds_orders）是执行单，状态机推进即驱动记账。
3. **客户资产物理隔离**，防混同（commingling）。
4. **对账：先验内部恒等，再拿外部反证。**
5. **逐物理钱包 1:1 直比**，不做五公式分层。
6. **差异按性质分类处置。**
7. **在途主动推、不干等**——区别于传统"挂账等下期自平"，我们在实时 1:1 模型里主动推资金单让账本追上外部。

### 0.3 术语与底层原理

- **append-only（只增不改不删）**：账本只往后追加流水，从不修改/删除已记录的行。余额不是存一个字段改来改去，而是把流水**加总**出来。记错只能追加冲正分录，不擦历史。`account_flows` 与底层 TB 转账均 append-only。这是监管对不可篡改审计的硬要求。
- **as-of 余额随时可查、无需物化快照**：因 append-only + 每笔带生效日，任意时刻余额 = `Σ(生效日 ≤ 截止点的流水)`，随时可现算、且结果可复现（老流水不变）。**故不物化 0 点快照**（见 §7 决策 1）。
- **canonical 流水模型**：内外两侧流水归一到**同一套字段模型**，匹配退化成同结构直比（见 §7 决策 2）。
- **effectiveDate（生效日/价值日）是"日期"，createdAt（入账时刻）是"完整时间戳"——两个字段、两个用途**（见 §2.4）。
- **余额字段用法**：外部收盘余额直用（外部真相）；内部 `balanceAfter` 只作缓存/交叉校验，真值从账本现算（见 §2.5）。

### 0.4 差异分类：5 态（残差公式 + 行业名对齐）

**残差 = delta − Σ在途签名额**（delta = 外部收盘 − 内部累计；在途 IN 记正 / OUT 记负）。前 4 桶命中即止、互斥穷尽；HELD 与前四者正交（"还没法对" vs "对完的结论"）。

| 桶（enum） | 行业名 | 判定 | 开案 |
|---|---|---|---|
| `MATCHED` | Matched / Reconciled（对平） | 残差=0 且流水全配平 | 否 |
| `IN_TRANSIT` | Timing difference / Outstanding item（时间差/在途） | 残差=0 且 在途行 > 0 | 是 |
| `SOFT_FLAG` | Compensating errors（抵销错误：余额平·明细不平） | 残差=0 且 无在途 且 流水异常 > 0 | 是 |
| `BREAK` | True (permanent) difference（真差异） | 残差 ≠ 0 | 是 |
| `HELD` | Pending reconciliation（待外部数据） | 该源该日数据未到齐 | 否（挂起） |

> 高层 taxonomy：行业把差异统称 **reconciling items**，分 **timing**（→ IN_TRANSIT）vs **permanent/true**（→ BREAK）+ **errors**（→ SOFT_FLAG 抵销错误）。命名保留行业词 BREAK/IN_TRANSIT/MATCHED；SOFT_FLAG 注"抵销错误"；HELD 为新增数据可用性态。

### 0.5 流水对账状态 tag（贯穿全流程的记忆）

每条流水（内部 `account_flow` + 外部账单行，**双向**）带对账状态：

| tag | 含义 | 下次 run |
|---|---|---|
| `UNRECONCILED` | 新流水，未对过 | 参与 |
| `MATCHED` | 已配平闭合 | **冻结、踢出对账池** |
| 开放异常 / `IN_TRANSIT` | 未配平 / 被非终态资金单暂解释 | **结转、每次重对** |

自洽性：`余额 delta ≡ Σ(未配平流水签名额)`——MATCHED 互相抵消掉出账，剩下开放项之和正好是余额差。这是残差公式的另一面。tag 是"虚拟快照的记忆"，让对账增量化、可复现、可审计。

## 1. 步骤 1 · 定起点 + 内部恒等校验

**标准要义**：定对账对象与期间，校验起点（期初=上期期末 rollforward），账本自身先平才谈对外。

### 1.1 应然做法

- **对账对象**：所有物理钱包——客户 `C_DEP` / `C_VIBAN`、公司 `F_OPS` / `F_SET` / `F_FEE` / `F_LIQ`，按 币种 × 钱包。
- **期间**：业务日 T-1，as-of cutoff（T-1 收盘时点）。
- **起点校验 = 内部恒等预门**：按币种验
  - 客户侧 `Σ CLIENT_ASSET ≡ Σ(CLIENT_PAYABLE + DEPOSIT_SUSPENSE)`
  - 公司侧 `Σ FIRM_ASSET ≡ Σ(FIRM_OPS + FIRM_SET + FIRM_FEE + FIRM_LIQ)`
  - 破 → 本 run 标 `INTERNAL_BREAK` **中止**、不做逐钱包比对。
- **每次都建 run**：恒等结果决定 run 是"中止(INTERNAL_BREAK)"还是"继续"，**不是**"要不要建 run"。

### 1.2 恒等的两层区分（关键认知）

| 层 | 会不会破 | 说明 |
|---|---|---|
| TB 双分录守恒（Σ全局借 = Σ全局贷 + 原子性） | **永不破** | TB 构造保证，记不出半条转账 |
| 业务恒等（客户资产 ≡ 客户负债，按币种） | **能破，但只在账务缺陷时** | 配错账户 / COA 码映射错 / 手动记账没守镜像 / 非原子多笔中途断 / seed 迁移错 |

**结论**：业务恒等破 = **账务代码/操作有 bug 的红色警报，不是正常业务状态**。且实时 1:1 COA 设计成每一中间步都保持恒等（如充值两步 `CLIENT_ASSET→DEPOSIT_SUSPENSE→CLIENT_PAYABLE`，DEPOSIT_SUSPENSE 与 CLIENT_PAYABLE 同在负债侧，每步都不破），连"操作中途瞬时不平"都不该出现。健康生产里应为 **0 次**；开发/重构期会撞到，且预门抓到正是它在干活（频率是**双峰**：代码对→0，代码错→系统性）。

### 1.3 破了怎么办：当 P0 账本完整性事故

不是普通对账差异（源真相坏了）。响应：

1. **中止对外对账**（预门已做）+ **实时告警**（page on-call / 财务 / 合规）。
2. **收敛/冻结受影响范围**（如该币种交易）——下游数字全部存疑。
3. **绝不自动修复**：定位根因（该币种 transfer / account_flow 日志找出破镜像的那笔）。
4. **受控更正**：经审批（CISO/CFO/MLRO）的更正分录 + 全审计；很可能触发 **VARA 重大差异通报**。
5. **治本 = 校验左移**：CI / 每次记账后 / 持续断言镜像恒等，别只靠 24h 日 run。日 run 预门是**最后一道网、非唯一一道网**。

> 罕见 ≠ 可省：罕见 + 灾难性正是"没准备好就出大事"的组合。v1 只做轻量四样——**检测（已有）+ 左移断言 + 响亮告警 + 详情呈现 + 中止**，不做自动修复。

### 1.4 INTERNAL_BREAK 时 run 详情呈现

| 区块 | 内容 |
|---|---|
| 顶部状态 | 显著 **INTERNAL_BREAK · 内部账本恒等破裂**（区别于普通 BREAK run） |
| 一句话 | "本次对账**已中止**，逐钱包比对**未执行**——账本自身先坏，需先修账本" |
| 恒等破裂明细 | 按币种：`客户资产合计 / 客户负债合计 / 差额`；公司侧 `FIRM_ASSET合计 / FIRM权益合计 / 差额`。仅列破的行 |
| 事故入口 | 升级/工单 + 根因排查链接（该币种 transfer 日志） |

**三条硬要求**：① **不**显示正常五桶驾驶舱（没跑）；② **严禁"空表 = 全清"**（空是"没跑"不是"没差异"）；③ 恒等明细数据已被预门 breaks[] + 审计捕获，缺的是前端呈现。

## 2. 步骤 2 · 两侧取数 + canonical 归一 + 数据完整性闸

**标准要义**：取内部账 + 外部独立来源，归一化到同口径。

### 2.1 内部侧

直接用 `account_flows`（append-only + effectiveDate），**不物化余额快照**——append-only 流水 + effectiveDate + 流水 tag 即"虚拟快照"，可复现可审计（决策 1）。

### 2.2 外部侧 · canonical 同构

银行 / HexTrust / 链账单**清洗成与 account_flow 同构的 canonical 流水模型**（决策 2）：同字段、同单位「分」、同方向语义。两侧同结构 → 一对一匹配退化成直比。

### 2.3 canonical 流水模型字段清单（内外对称）

| 字段 | 类型 | 说明 |
|---|---|---|
| `walletRef` | id | 归属物理钱包 |
| `direction` | IN / OUT | 方向 |
| `amount` | int（**分**） | 最小单位整数 |
| `externalRef` | string | 对账键（链上 txHash / 银行入账号） |
| `effectiveDate` | **date** | 价值日 / 业务日（as-of 过滤用） |
| `bookingTime`（内部 = `createdAt`） | **datetime** | 入账/记账时刻（排序、边界卡点、审计、复现） |
| `matchState`（tag） | 枚举 | §0.5 对账状态 |

### 2.4 effectiveDate（date）vs bookingTime（datetime）—— 两个字段两个用途

- **effectiveDate 保持"日期"**：银行价值日本就是日期粒度；日对账截止点是日界，"生效日 ≤ 截止日"用日期比即够、无歧义。硬做成 datetime 反而混淆语义。
- **时间放 bookingTime/createdAt（完整时间戳）**，承担：① 同日内排序算逐笔余额；② "生效日=截止日"那天的**边界按物理时刻卡**；③ 审计；④ 复现某次 run（`createdAt ≤ 那次 run 时刻`，append-only 让 createdAt 也不可改）。

### 2.5 余额字段用法

- **外部收盘余额 → 直接用**（外部真相，即余额级比对的外部输入）；额外拿**逐笔余额**做**账单完整性交叉校验**（相邻余额差 ≠ 该行金额 → 账单缺行 → 一条对账发现）。
- **内部 balanceAfter → 只当缓存/交叉校验**：它是记账那刻算的，**平账回填过去日期流水后不自动重算 → 会陈旧**。对账内部数字**优先从账本现算**（TB 实时余额 / Σaccount_flows 到截止点），并断言 `balanceAfter == Σ流水到此` 以抓数据质量问题。
- **余额字段不能替代流水匹配**——光比余额是弱对账（SOFT_FLAG 抵销错误会蒙混过关）。余额给"余额级"，流水给"流水级"，**两层都要**。

### 2.6 数据完整性闸 + 结算轴 ≠ 上报轴

- **数据完整性闸**：按源判"该业务日数据到齐没到齐"——到齐才对；没齐 → 该源钱包标 `HELD` 挂起，**绝不拿旧值硬对**。
- **两根独立的轴**：结算是否发生 ≠ 账单是否到齐。即时支付轨道（UAE Aani / SEPA Instant 等）**周末照样结算**、但账单营业日才出 → 仍 `HELD` 等账单，别拿旧收盘硬对（否则内部动了、外部没上报 → **误判假 BREAK**）。
- **主判据 = 数据驱动**（账单到没到）；**日历只做预期/告警**（营业日该来没来 → 告警，即账单延迟/丢失）。
- **节假日不跳过 run**：虚拟币 7×24 每天正常对；法币非营业日的钱包走 `HELD`，等下个营业日账单到齐**一把补对**（Fri→Mon 一次对到最新完整截止点，靠累计余额 + tag 结转天然成立）。周末发起的法币提现挂 `IN_TRANSIT`，周一账单集中清算自愈。

## 3. 步骤 3 · 比对匹配

**标准要义**：逐笔比对，1:1 / 一对多 / 模糊 + 容差，标 reconciling items。

### 3.1 两层

- **余额级**：累计 as-of——`delta = 外部收盘 − 内部累计余额`（内部按 `effectiveDate ≤ cutoff` 过滤，天然含全部历史）。
- **流水级三轮**：Pass1 同 `externalRef` 精确 → Pass2 金额+方向+时间窗（容差）模糊 → Pass3 在途（孤儿外部行 ↔ 非终态资金单）。

### 3.2 tag 结转（增量化）

- `MATCHED` 冻结踢出池；开放异常 + 在途结转。每 run **只对"未决 + 新增"**，工作量 O(未决) 而非 O(全历史)。
- **自愈机理**：当天新到的内部结算流水去配一条历史遗留的外部孤儿（那条在途行）→ 配上 → 在途消解转 MATCHED。
- **持续差异**：累计余额保证一个未解决差异每天被 re-observe、继续报——正是 aging 信号源。

## 4. 步骤 4 · 分类 → 开案

**标准要义**：定根因，归 timing vs true difference，登记待查项。

- 按 §0.4 残差公式分 5 态。非 MATCHED/HELD → 开**钱包级 case**（跨日唯一 OPEN/钱包），带 severity（额度分级），把问题流水（tag=开放/在途）挂 case。
- **run = 当日冻结观测（不可变快照）；case = 跨日追踪实体。** 差异没解决，每天 run 都 re-observe 它、继续报。

---

## 5. 步骤 5 · 处置

**标准要义**：timing 挂账待自平；true 须调整/补录/冲正。

| 桶 | 应然处置 |
|---|---|
| `IN_TRANSIT` | 等自愈（结算信号到 → 资金单自动结算 → 下 run 自愈）→ **aging 超 SLA**（按该工具预期结算时间）没好 → **推单**（同步查唯一回执 / 人工三件套）。铁律：只调 `advance` 不直写账本、回填生效日透传。**推单挂 maker-checker（推 ≠ 批）** |
| `BREAK` | 先剥掉里面的在途层（同 IN_TRANSIT 处置）→ 剩纯真差异 → **真差异处置留空**（补/冲正/冲销/豁免/偿付，见 §9） |
| `SOFT_FLAG` | 逐条查未配平行：① 多为 matcher 漏配 → 调匹配规则重配 → 转 MATCHED；② 真两侧对冲错 → 走真差异处置（留空）；③ 错分在途 → 重分类。**不动钱、强制人看过** |
| `HELD` | 等该源数据到齐 → 累计余额一把补对 |

> **在途死结**：若结算信号永久丢失（webhook 漏）且无人推单 → 资金单永远非终态 → in-transit 永不自愈。故 aging/SLA/升级 + 理想的"对账触发主动反查（re-poll）"是防死结的闸——in-transit **不保证**自愈。

---

## 6. 步骤 6 · 复核签核 + 留档

**标准要义**：maker-checker、报告 sign-off、审计留痕、留档。

- **干净 run（全 MATCHED）→ 自动认证**，无需人工复核（风险化对账的 auto-certify）。
- **有人工平账 → 该动作走复核签核**（maker-checker：推 ≠ 批；可按 severity 分级审批人）。**复核挂在"人工干预动作"上，不是挂在"run 变 pass"上**；自动自愈（无人工）免复核。
- **aging + SLA**：OPEN 差异按账龄计时，超期自动升级 MLRO/CFO。
- 已有：审计留痕（每步带 traceId）+ 不可变 run/逐钱包快照 + Run/Case/External 驾驶舱。
- **留空待做（VARA 合规）**：重大差异通报 VARA、记录 ≥8 年留存、每月客户账单（见 §9）。

## 7. 关键设计决策汇总（8 条）

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 内部取数：物化快照 vs 现算 | **乙·不物化** | append-only 流水 + effectiveDate + tag 即虚拟快照；快照是冗余缓存。回填补账场景下物化快照反而变脏 |
| 2 | 两侧归一 | **甲·canonical 同构** | 外部洗成与 account_flow 同结构，匹配退化成直比 |
| 3 | 匹配 | 累计 as-of 余额 + 流水 tag 结转 | 余额层累计防漏、明细层结转只干未决；`delta ≡ Σ未配平` |
| 4 | 差异分类 | 5 态（+HELD） | 每桶驱动不同处置；HELD 与前四正交 |
| 5 | 在途处置 | 等 → aging/SLA → 推单 + maker-checker | timing 别乱动；改账必双人 |
| 6 | 数据完整性闸 | 数据未齐挂起 HELD | 解耦结算轴/上报轴，杜绝假 break |
| 7 | 复核 | 干净自动认证；人工平账才签核 | 复核挂人工干预动作 |
| 8 | 恒等破 | 当 P0 事故 + 校验左移 | 源真相坏、下游全存疑 |

## 8. 应然 vs 代码实际 — 差距表

| 维度 | 应然 | 代码实际 | gap |
|---|---|---|---|
| 内部恒等预门 | 先验守恒、破则中止 | 已实现 | ✓ 对齐 |
| 每 run 必建 / 逐钱包快照定格 | run 无条件建、快照不可变 | 已实现 | ✓ 对齐 |
| 前 4 桶 + 残差公式 | MATCHED/IN_TRANSIT/SOFT_FLAG/BREAK | 已实现 | ✓ 对齐 |
