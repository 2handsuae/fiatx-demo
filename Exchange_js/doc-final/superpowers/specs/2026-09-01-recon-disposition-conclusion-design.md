## §0 为什么要重写

### §0.1 现状：一个按钮挂在所有行上

`ReconciliationCasesDetailPage.tsx:761` 的注释是原话：**「开调账单入口——所有 5 类行都给，不按 matchType 挑着给」**。渲染处只按权限 + `kase.status==='OPEN'` + `explainedByAdjustmentNo` 门控，**不看行的类型**。于是在途行、已匹配行上都挂着「开调账单」。在途那一格点下去会造成重复计账（钱在路上，账先抹平，落地时账本再记一次）。

### §0.2 上一版设计为什么作废

上一版（2026-08-29）的解法是一张 `形状 × 账簿 → 动作` 的判定表。**次日**落地的 break-scenarios 那轮把破口铺到 15 个成因，并专门建了三个「展示位」，设计原话是「同一个形状三条差异、三种相反处置摆在一屏」。两者对撞：

用 2026-09-01 在 main 栈实跑的 `recon:demo:break`（15/15 场景检出、10/10 钱包桶正确）取真实数据：

| 展示位 | 案件 | 三条差异的形状 | 上一版判定表会给 | break-scenarios 要的 |
|---|---|---|---|---|
| 甲 | REC20260901-007（客户 CU2601014381 · AED）| ④⑩⑪ 全是 `AMOUNT_MISMATCH` | 三行**全给「冲正」** | ④冲正 / ⑩不动账 / ⑪冲正 |
| 乙 | REC20260901-010（客户 CU2601010484 · AED）| ③⑦⑧ 全是 `ORPHAN_INTERNAL` | 三行**全给「冲销」** | ③不动账 / ⑦冲销 / ⑧冲销 |
| 丙 | REC20260901-004（客户 CU2601017625 · USDT）| ⑤⑨ 全是 `ORPHAN_EXTERNAL` | 两行同一句说明 | ⑤走充值域 / ⑨找银行 |

展示位的全部价值就是「同样的形状、相反的答案」。判定表键在形状上，甲三行长一样、乙三行长一样——**这次收口把它自己要演的那件事演没了**。

更要命的是 ③ 和 ⑫：它们的形状是 `ORPHAN_INTERNAL`，判定表必然给出「冲销」，而正确答案是**不该动账**（③ 我方账是对的、⑫ 下期自然平）。按下去账就错了。

上一版 §0.1 第一行自己写着「**差异类型不能直接映射到动作**」，然后 §2 建了一张按类型映射的表。**这不是实现问题，是那个目标机器达不到**：15 个成因进门时塌缩成 6 格（实际只用到 5 格），信息在那一刻就丢了。

### §0.3 那机器到底知道什么

跑批实测，机器手上只有：形状（3 种差异 + 已匹配 + 在途）× 账簿（客户 / 公司）。**15 个成因里只有一个是机器认得出来的**：

⑦ 我方重复入账 —— 银行报一次、我方入两笔，两笔挂同一个参考号。REC20260901-010 的实测数据：

```
MATCHED          ext 730000  int 730000  ref ZB20260901159A97236B
ORPHAN_INTERNAL  ext   None  int 730000  ref ZB20260901159A97236B   ← 同号同额的双胞胎
ORPHAN_INTERNAL  ext   None  int 200000  ref ZB2026090110DF0A78FF   ← 无双胞胎
ORPHAN_INTERNAL  ext   None  int 910000  ref ZB202609011C5D76D612   ← 无双胞胎
```

其余 14 个成因，机器分不出来。**那是财务去查的活，系统的责任是把查证结论收下来、存下来、并据此给出口。**

### §0.4 讨论中确立的口径（结论，不要翻案）

| 结论 | 依据 |
|---|---|
| **同形状的行必须给同一个按钮** | 给不同按钮就是假装机器知道它不知道的东西 |
| **差异化发生在人答完之后，不在按钮上** | 「谁错了」是业务判断，不是数据属性 |
| **豁免与核销不是一回事** | 豁免 = 不动账、账实永久不符；核销 = 动账、差额进损益、账实相符。上一版把两个词混着用了 |
| **「我记 35、外部 35.02」既不是豁免也不是核销，是冲正** | 业主 2026-09-01 裁定。钱真在银行那儿，客户就该有 35.02，我方记少了——`DEPOSIT_AMOUNT_CORRECTION` 正是干这个的 |
| **15 个场景里没有一条需要豁免** | 逐条论证见 §6。③⑨⑩ 等对方改、⑫ 下期自平、⑪ 归冲正、⑤⑥⑬ 回业务域。**不是"划到本轮不做"，是"论证过不需要"** |
| **手续费轧差留在客户钱包上，客户承担** | 业主 2026-09-01 裁定，`decisions.md [2026-08-28]` 相应条目改写，只保留这一种口径 |
| **挂起不让案子变绿** | 差异还在，只是知道了原因。案子照旧红着，从「没人碰过」变成「已定性 · 等对方 · 张三 9/1」。第六幕不粉饰 |
| **本轮零引擎改动** | 残差公式、五桶规则、销案判据一律不碰 |

## §1 范围

**做**

1. 入口收口：已匹配无按钮 ｜ 在途给「去推单」｜ 其余三种差异给**「处置」**
2. 处置弹层第一屏：**定性三选一** + 必填查证说明，无兜底档
3. 结论落库：新表 `reconciliation_dispositions`
4. 出口判定：后端纯函数，18 格（3 形状 × 2 账簿 × 3 定性）
5. 改账出口沿用一期调账单：成因收窄到 1–2 个（`REASON_SPECS` 加 `family`），方向改只读
6. 挂起出口 / 转业务域出口：只记结论，不落账
7. ⑦ 的机器佐证：同参考号双胞胎提示
8. 案件页与案件列表显示定性结论
9. 审计留痕（铁律①）+ RBAC 登记
10. `decisions.md` 订正 + `modules/v8-recon.md` / `demo/script.md` 同步

**不做**

豁免 ｜ 核销 ｜ 案件级开单入口 ｜ **任何对账引擎改动** ｜ 充值域补录入口（归 V4）｜ 公司账簿的冲销成因码 ｜ SLA / aging / 复核签核 ｜ 演示种子改动（② 留着，`recon-demo.ts` 不动）｜ 定性的撤销与重开（见 §10）

## §2 入口：一行一个按钮

| 行 | 按钮 | 说明 |
|---|---|---|
| 已匹配 | 无 | 两边对上了，没有可处置的东西 |
| 在途 | **去推单** | 链到资金单页。在途不是差异，是已知在路上——它的动作是推单，不是处置 |
| 金额不对 / 我有外无 / 外有我无 | **处置** | 不分账簿、不分形状，同一个词 |
| 已被调账单解释（`explainedByAdjustmentNo` 非空） | 「已解释 · ADJxxx」链接 | 维持现状 |
| 已定性（本表有记录） | 「已定性 · <出口> · <人> <日期>」链接 | 新增，见 §7.3 |

按钮的权限门控沿用既有约定：**以权限控整个按钮的显隐，不是禁用态**（`CustomerDetail.tsx` 等既有写法）。

案件 `status !== 'OPEN'` 时不给处置入口（同一期 Fix 5）。

## §3 第一屏：定性

> 这条差异，你查下来是谁的问题？

| 选项 | 枚举 | 覆盖的成因 |
|---|---|---|
| ⓐ **我方记错了** | `OURS_WRONG` | ②④⑤⑥⑦⑧⑪⑬⑭⑮ |
| ⓑ **对方记错了 / 对方还没报** | `THEIRS_WRONG` | ③⑨⑩ |
| ⓒ **都没错（时点差，下期自平）** | `NEITHER_WRONG` | ⑫ |

**必选，无兜底档**——理由同一期七成因：兜底档一开，说不清的全往里塞，久了变垃圾桶、审计价值归零。

**必填「查证说明」**（内部口径，自由文本）。这是查证过程的唯一留存物；没有它，明天换个人还得从头查一遍。

⚠️ ⓑ 与 ⓒ 的出口相同（都是挂起），差别在**后续期待**：ⓑ 要发函催对方，ⓒ 什么都不用做、等下期。两者的说明文案与案件页展示词不同，故保留为两个选项，不合并。

**⑦ 的机器佐证**：当这条 `ORPHAN_INTERNAL` 行的 `externalRef` 在同一案件的**已匹配行**里出现且金额相同时，第一屏显示一行提示：

> 💡 已匹配列表里有一条同参考号同金额的行（`ZB20260901159A97236B`）——银行只报一次、我方入了两次。

这是 15 个成因里唯一由机器给出的证据，不出现时不显示占位。

## §4 第二屏：出口判定表

出口由 `(定性 × 形状 × 账簿)` 唯一决定。**这才是机器该管的部分**——加上定性这一维之后，剩下的确实是可判定的。

| 形状 | 账簿 | ⓐ 我方错 | ⓑ 对方错 | ⓒ 都没错 |
|---|---|---|---|---|
| 金额不对 | 客户 | `ADJUST` · 冲正 | `HOLD` | `HOLD` |
| 金额不对 | 公司 | `ADJUST` · 补记 | `HOLD` | `HOLD` |
| 我有外无 | 客户 | `ADJUST` · 冲销 | `HOLD` | `HOLD` |
| 我有外无 | 公司 | `NO_CODE` | `HOLD` | `HOLD` |
| 外有我无 | 客户 | `ROUTE` · 转业务域 | `HOLD` | `HOLD` |
| 外有我无 | 公司 | `ADJUST` · 补记 | `HOLD` | `HOLD` |

`ROUTE` 的目的地由**该行的外部流水方向**决定，两个目的地本期都未开放，只记结论：

| 外部方向 | 含义 | 目的地 |
|---|---|---|
| IN | 外面真有一笔客户入金我方没记 | **充值域**补录（⑤ 漏监听充值、⑬b 记错钱包接收端）|
| OUT | 外面真有一笔钱出去了我方没记 | **提现／退汇域**认领（⑥ 退汇，承接 BACKLOG「SUCCESS 后退汇应归对账认领」）|

四种出口：

| 出口 | 动账 | 案子会平吗 | 落什么 |
|---|---|---|---|
| `ADJUST` | ✅ 走一期调账单 + 审批 | ✅ 落账后重对账自愈 | 定性记录 + 调账单 |
| `ROUTE` | ❌ | ❌ 等业务域补录 | 只有定性记录 |
| `HOLD` | ❌ | ❌（⑫ 下期自平） | 只有定性记录 |
| `NO_CODE` | ❌ | ❌ | 只有定性记录 |

### §4.1 三格「不给动账」为什么

**外有我无 + 客户账簿 + 我方错 → `ROUTE`**：外面真有一笔客户资金进出我方没记。用调账把它补上 = 没跑 KYT、没过合规闸、没有客户单号，从后门踩铁律②。这条与 `decisions.md [2026-08-28]`「调账单不得用于补记真实发生的客户资金流入或流出」是同一条。正解永远是回业务域把流程跑起来（入方向归 V4 充值、出方向归 V5 提现／退汇认领，两个入口都在 BACKLOG）。

**我有外无 + 公司账簿 + 我方错 → `NO_CODE`**：现有七码里公司账簿只有银行利息、银行杂费两个补记码，没有「撤销我方错记」的码。演示里也没有这种案子，本期不补码。

**所有 ⓑ / ⓒ → `HOLD`**：我方账是对的，动账反而把对的改成错的。

### §4.2 族划分与成因收窄

族划分（七码分完，无重叠无遗漏；已与 `adjustment-rules.ts` 的 `REASON_SPECS` 逐格核对）：

| 族 | 成因码 | 账簿 |
|---|---|---|
| `CORRECT` 冲正 | `DEPOSIT_AMOUNT_CORRECTION` · `WITHDRAW_AMOUNT_CORRECTION` | CLIENT |
| `REVERSE` 冲销 | `DEPOSIT_DUPLICATE_REVERSAL` · `DEPOSIT_SIGNAL_VOID` · `WITHDRAW_VOID_REFUND` | CLIENT |
| `RECORD` 补记 | `BANK_INTEREST` · `BANK_CHARGE` | FIRM |

方向从行推导（逻辑已存在于 `rowAdjustmentPrefill`，本轮只是从可改下拉改成**只读 + 一句推导依据**）。统一口径 `差额 = 外部 − 内部`，内部偏高就减、偏低就加：

| 形状 | 推导 |
|---|---|
| 金额不对 | 差额符号：负 → 减，正 → 加 |
| 我有外无 | 内部流水方向取反：IN → 减，OUT → 加 |
| 外有我无 | 外部流水方向照搬：IN → 加，OUT → 减 |

候选表 `reasonsFor(book, family, direction)`（六格里四格零选择）：

| 族 | 方向 | 候选 |
|---|---|---|
| 补记 | 减 | 银行杂费 —— 定死 |
| 补记 | 加 | 银行利息 —— 定死 |
| 冲销 | 减 | 重复入账撤销 · 充值撤销 —— 2 选 1 |
| 冲销 | 加 | 提现撤销退回 —— 定死 |
| 冲正 | 减 | 充值金额更正 —— 定死 |
| 冲正 | 加 | 充值金额更正 · 提现金额更正 —— 2 选 1 |

## §6 平账：十五条里能平十条

销案的机器判据不变（`残差 = 0 且 无在途 且 流水异常 = 0` → MATCHED → 自动销案，见 `bucket-classifier.ts`）。三条出路各自这样走：

| 出口 | 机制 | 案子会平吗 |
|---|---|---|
| 冲正 / 冲销 / 补记 | 落分录 → 内部余额动 → 残差归零；同时按「外部行 id / 内部流水 id」把差异行标为已解释 → 异常数 −1 → 下轮重对账**自动销案** | ✅（一期已跑通） |
| 去推单 | 资金单推到终点、回填生效日 → 在途落地 → 残差归零 | ✅（推单那轮已跑通） |
| 挂起 | **什么都不动** | ❌（⑫ 下期自然平） |
| 转业务域 | 只记结论 | ❌ 直到业务域真把钱补进来 |

| ⑬a | 记错钱包 · 发出端 | 我有外无 | 客户 | ⓐ | 冲销 | ✅ |
| ⑬b | 记错钱包 · 接收端 | 外有我无（IN） | 客户 | ⓐ | 转业务域 · 充值 | ❌ |
| ⑭ | 银行杂费 | 外有我无 | 公司 | ⓐ | 补记 | ✅ |
| ⑮ | 银行利息 | 外有我无 | 公司 | ⓐ | 补记 | ✅ |

**能平 10 条**（①②④⑦⑧⑪⑫⑬a⑭⑮），**不能平 6 条**（③⑤⑥⑨⑩⑬b）。

这就是第六幕要讲的那句话：**对账台是分诊台，不是万能钥匙。十五种差异只有十种我们自己修得了；三种得等对方改、三种得回到业务流程里重新跑一遍。** 记分牌演到最后仍有红——这不是缺陷，是账实确实不符，我们不粉饰。

### §6.1 豁免为什么不需要

豁免的定义是「差异真实、永远不会消失、我方决定不动账」。逐条查 15 个成因，没有一条落在这个定义里：③⑨⑩ 对方会改、⑫ 下期自平、⑤⑥⑬ 钱真的进出了必须补流程、其余都是我方能改的。**⑪ 舍入差曾被误判为豁免场景**——但演示数据里外部**收盘余额**也跟着变了，即钱确实在对方那儿，所以它是冲正。

日后若出现「钱不在、差异永久」的真实场景（例如加密币精度低于链上精度导致的尘埃），再单独设计豁免与核销，届时须先在 `decisions.md` 写清两者的分界。
