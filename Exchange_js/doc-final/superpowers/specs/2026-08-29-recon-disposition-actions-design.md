# 对账案件处置动作收口（平账一期半）

> 状态：设计定稿，待写实施计划
> 日期：2026-08-29
> 前序：`2026-08-27-recon-adjustment-order-design.md`（调账单一期）

---

## §0 为什么要做这一轮

一期把调账单做出来了，但案件页上的入口是**一个通用的「开调账单」按钮，挂在全部 5 类差异行上，不按类型挑**。业主走查时直接指出问题：在途那一行也有这个按钮，而在途明明是推单的活。

往下查，这个通用入口有三个毛病：

1. **在途行给开调账单会造成重复计账**——在途的意思是钱确实在路上、资金单还没走完；开调账单把差额抹平，等钱真落地时账本再记一次。
2. **已匹配行也有这个按钮**——已经对上的流水给开单入口，没有任何业务含义。
3. **有几类差异根本没有正确的动作**（客户侧「外有我无」要走充值域补录、未归属账户要先归属），通用按钮让它们看起来都能处理。

业主提出按会计语言收口（冲正 / 冲销 / 补记）。本设计落这一条，并把「没有正确动作」这件事显式化。

### §0.1 讨论中确立的口径（这些是结论，不要翻案）

| 结论 | 依据 |
|---|---|
| **差异类型不能直接映射到动作** | 同一个形状可能有相反的成因：客户侧「外有我无」既可能是客户真打了钱（走补单），也可能是公司收支（补记）；「我有外无」既可能是我方误记（冲销），也可能是银行漏报（我方账是对的，不该动账） |
| **成因是核心，不是装饰** | 七个成因码刻意没有兜底项，就是逼运营在开单前答「为什么」 |
| **冲正 / 冲销 / 补记 是三族，不是两族** | 银行利息 / 银行杂费**不是纠错**——外部真发生了一笔我方还没记的事，账变对的方式是新增一笔，不是改掉原来那笔 |
| **豁免不是「不能改账」的同义词** | 豁免 = 差异真实、永远不会消失、我方决定不动账。真实触发条件是「金额太小 / 挂太久 / 确定查不动」，**跟差异类型无关**。银行漏报这类还有指望的，正解是挂起追踪，不是豁免 |
| **豁免必须处理余额差，不只是流水行** | 只标掉流水行，余额差还在 → 残差不为零 → 桶仍是破口 → 案子照样关不掉。会计上它是**调节项**（银行余额 + 调节项 = 账面余额），结构上跟引擎里已有的「在途」是同一类：已解释、但账上没动的差额 |
| **豁免与挂起本轮都不做** | 业主拍板。因此「没有正确动作」的差异行本轮只能明说没有 |
| **未归属账户演示场景移除** | 业主拍板。⚠️ 只删种子注入，**引擎的检查与其单测保留**（`wallet-recon-run.service.spec.ts` 「无主外部余额头 → 开 BREAK case」）。设计者意见：这一类在监管口径下是真问题，去掉后演示讲不到这道检查——记录在案，业主已知悉 |

## §1 范围

**做**

1. 行 → 动作判定表收口
2. 三族 × 推导方向 → 成因候选收窄；方向改只读
3. 演示种子：删「未归属外部账户」，加「干净的重复入账」

**不做**

豁免 · 挂起 · 补单（充值域补录）· 账户归属 · 案件级开单入口 · 公司账簿的冲销成因码 · 豁免金额门槛 · 未归属账户的案件页说明

## §2 判定表：一行只有一个动作

| 差异行 | 账簿 | 动作 | 界面 |
|---|---|---|---|
| 已匹配 | — | 无 | 空 |
| 在途 | — | **去推单** | 链到资金单页 |
| 金额不对 | 客户 | **冲正** | 按钮 |
| 金额不对 | 公司 | **补记** | 按钮 |
| 我有外无 | 客户 | **冲销** | 按钮 |
| 我有外无 | 公司 | ❌ 无出口 | 「本期公司账簿只做补记」 |
| 外有我无 | 客户 | ❌ 无出口 | 「客户资金入账须走充值域补录，本期未开放」 |
| 外有我无 | 公司 | **补记** | 按钮 |

已经被调账单解释过的行（`explainedByAdjustmentNo` 非空）不走本表，维持现状显示「已解释 · ADJxxx」并链到那张单。

### §2.1 两处「无出口」为什么是无出口

**外有我无 + 客户账簿**：冲销的语义是「这笔本就不该记，撤掉」，而外有我无意味着**我方压根没记过**——撤销一个不存在的记录说不通。这一格的正解永远是补单（走充值域把流程跑起来，过 KYT 与合规闸）。这也正是一期 §4 边界线的同一条：**调账单不得用于补记真实发生的客户资金流入或流出**。

**我有外无 + 公司账簿**：现有七码里公司账簿只有银行利息、银行杂费两个，都是「补记真实发生的事」，没有「撤销我方错记」的码。演示里也没有这种案子，本期不补码。

### §2.2 「金额不对 + 公司账簿 → 补记」为什么说得通

公司账簿没有冲正码，但这一格仍然有解：银行扣了 2.05、我方记了 2.00，差的 0.05 **本身就是一笔真实发生、我方还没记的杂费**——补记 0.05 即可，不需要「改掉原来那笔」。所以补记同时覆盖了公司账簿的金额不符。

⚠️ 演示数据里**没有**公司账簿金额不符的案子，这一格靠 `reconRowAction.spec.ts` 的单测覆盖，不靠走查。

## §3 三族 × 方向 → 成因候选

### §3.1 族划分（七码分完，无重叠无遗漏）

| 族 | 成因码 | 账簿 |
|---|---|---|
| **冲正**（把金额改成对的） | `DEPOSIT_AMOUNT_CORRECTION` · `WITHDRAW_AMOUNT_CORRECTION` | CLIENT |
| **冲销**（撤销这笔入账） | `DEPOSIT_DUPLICATE_REVERSAL` · `DEPOSIT_SIGNAL_VOID` · `WITHDRAW_VOID_REFUND` | CLIENT |
| **补记**（记一笔公司自己的收支） | `BANK_INTEREST` · `BANK_CHARGE` | FIRM |

### §3.2 方向从行推导（逻辑已存在，只是被渲染成了可改下拉）

| 行类型 | 推导 |
|---|---|
| 金额不对 | 差额符号：负 → 减，正 → 加 |
| 我有外无 | 内部流水方向取反：IN → 减，OUT → 加 |
| 外有我无 | 外部流水方向照搬：IN → 加，OUT → 减 |

统一口径：`差额 = 外部 − 内部`，内部偏高就减、偏低就加。三族通用。

### §3.3 候选表（最多两个，六格里四格零选择）

| 族 | 方向 | 候选 |
|---|---|---|
| 补记 | 减 | 银行杂费 —— 1 个，直接定死 |
| 补记 | 加 | 银行利息 —— 1 个，直接定死 |
| 冲销 | 减 | 重复入账撤销 · 充值撤销 —— 2 选 1 |
| 冲销 | 加 | 提现撤销退回 —— 1 个，直接定死 |
| 冲正 | 减 | 充值金额更正 —— 1 个，直接定死 |
| 冲正 | 加 | 充值金额更正 · 提现金额更正 —— 2 选 1 |

## §5 演示数据变更

**删**：第 9 条 `ORPHAN_DEPOSIT`（未归属外部账户）——注入、manifest 条目、identity 自检里的相应计数。**引擎的 `unattributed` 分支与其单测保留。**

**加**：一条干净的重复入账（同一笔充值在账本上入了两次，银行只有一笔）→ 期望 `BREAK` / `ORPHAN_INTERNAL` / 客户账簿 → 落在「冲销」按钮上。

**为什么必须加**：不加的话，冲销唯一的落点是「银行漏报明细」那条案子，而它的真相是**我方账其实是对的**——按钮在，按下去业务上站不住。三个族里有一个没有干净的演示位，等于这次收口只演出了三分之二。

**数量对冲**：9 个场景 8 个案件不变，`recon:demo:break` 基线数字不变（钱包计数可能 ±1，以实跑为准）。

## §8 已知短板（本轮不修，登记在案）

1. **`BANK_RETURN` 演示数据自相矛盾**：造了一进一出净额为零的两条流水，又把外部收盘单独压低了同样的金额——现实里没有哪个事件同时产生这两样。该案子因此没有任何一条流水行能解释它的余额差。
2. **加密币演示金额是尘埃级**（0.000047 USDT）：种子把最小单位当成了整币，屏幕上不好看。不影响逻辑。
3. **「我有外无 + 客户」的按钮仍可能被点错**：冲销对「我方误记」是对的，对「银行漏报」是错的，而系统分不出这两种真相。本轮靠必填的内部原因兜；根治要等挂起与豁免。
4. **公司账簿没有冲销码**：见 §2.1。
5. **没有案件级开单入口**：余额差若没有任何流水行解释（如短板 1 那种），本轮无法开单。
