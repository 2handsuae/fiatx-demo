# C5 — Audit Evidence Export Workflow

## 1. 产品背景与目的

### 1.1 业务背景

Exchange_js 平台在监管合规框架（UAE VARA）下，**所有重要系统操作**均被记录在 `audit_log_events` 表中。当监管机构发起检查、内部合规审计或事件调查时，合规人员需要将指定的审计日志记录导出为结构化证据包，提交给监管方或留存备查。

这一导出行为本身属于**高敏感操作**——对哪些数据进行了打包、谁批准了导出、谁下载了包文件，都必须完整记录且不可篡改。

### 1.2 产品目标

| 目标 | 描述 |
|---|---|
| **合规可证明性** | 导出的每一份证据包都有完整的审批链，可向监管机构举证"谁授权、谁执行、谁下载" |
| **双人治理** | 导出申请须经独立审批，申请人（Maker）和审批人（Checker）必须是不同的人 |
| **防篡改验证** | 每份证据包携带 SHA256 摘要，接收方可独立验证包体完整性 |
| **完整操作追踪** | 导出操作的全生命周期（申请→审批→生成→下载）均写入审计日志，且该日志本身也在审计体系内 |

### 1.3 范围

本文档描述 **C5 Audit Evidence Export** 工作流的完整产品规格，包括：
- 功能流程与状态机
- 用户角色与权限
- 审计事件序列
- API 规格
- 错误场景与边界条件

## 2. 用户角色与权限

### 2.1 参与角色

| 角色代码 | 显示名称 | 在本流程中的职责 |
|---|---|---|
| `COMPLIANCE_OFFICER` | Compliance Officer | **Maker**：发起导出申请，选择要导出的审计日志记录 |
| `MLRO` | Money Laundering Reporting Officer | **Checker**：审批导出申请 |
| `SUPER_ADMIN` | Super Administrator | 可取消任意状态的申请（含他人申请） |

> 审批策略（`AUDIT_EVIDENCE_EXPORT_APPROVAL`）：checkerRoles = `MLRO`，timeoutHours = 24，allowCancel = true。

### 2.2 SoD（职责分离）规则

| 规则 | 描述 |
|---|---|
| Maker ≠ Checker | 提交申请的用户不能同时审批自己提交的申请 |
| Checker 角色限制 | 只有 `MLRO` 角色可以审批，其他角色调用审批接口返回 403 |
| SUPER_ADMIN 旁路 | SUPER_ADMIN 可以绕过 Maker ≠ Checker 规则，但系统会在审计日志中记录 `metadata.superAdminBypass=true` |

## 4. 功能流程详述

### 4.1 整体流程概览

```
┌─────────────────────────────────────────────────────────────────────┐
│                    C5 Audit Evidence Export Flow                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Maker (Compliance Officer)      System             Checker (MLRO)  │
│         │                          │                      │         │
│  [1] 选择审计记录                  │                      │         │
│  POST /evidence-packages ──────►  │                      │         │
│         │                    创建 Package               │         │
│         │                    创建 ApprovalCase           │         │
│         │                    写 EXPORT_REQUESTED ──────►│         │
│         │                          │               [2] 查看申请     │
│         │                          │               审批/拒绝/取消   │
│         │                          │◄──────────── POST approve      │
│         │                    写 APPROVAL_GRANTED        │         │
│         │                    异步生成包体                │         │
│         │                    写 GENERATION_COMPLETED     │         │
│  [3] 查看 READY 包                 │                      │         │
│  GET /evidence-packages/:id ───►  │                      │         │
│  GET /:id/download ────────────►  │                      │         │
│         │                    写 PACKAGE_DOWNLOADED       │         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 Step 1 — Maker 提交导出申请

**触发入口**：Audit Center → Audit Logs → 选择记录 → 导出证据包

**操作步骤**：
1. Maker 在审计日志列表页勾选要导出的记录（`selectedEventIds`）
2. 填写导出说明（可选）
3. 点击「提交导出申请」

**系统响应**（原子操作）：
1. 调用 `AuditLogsService.prepareEvidenceExportSelection()` 预计算选中记录
2. 创建 `AuditEvidencePackage`（`status=PENDING_APPROVAL`），生成请求摘要和 manifest
3. 创建 `ApprovalCase`（`actionType=AUDIT_EVIDENCE_EXPORT_APPROVAL`，`status=PENDING`）
4. 更新 `AuditEvidencePackage.approvalCaseId` 绑定关联
5. 写入审计事件 `EXPORT_REQUESTED`

**幂等性**：相同 `packageNo` 的 `EXPORT_REQUESTED` 事件通过 `requestId` 去重，重复提交不产生重复审计记录。

### 4.3 Step 2 — Checker 审批

**触发入口**：Control Gates Center → Approvals → 找到类型为 `AUDIT_EVIDENCE_EXPORT_APPROVAL` 的待审批单

**审批通过**：
- `ApprovalCase.status → APPROVED`，`executionStatus → EXECUTED`
- 系统通过事件监听（`ApprovalEvents.APPROVED`）触发 `AuditEvidenceExportApprovalService.handleApprovedApproval()`
- 写入 `APPROVAL_GRANTED` 审计事件
- **异步执行**：调用 `AuditLogsService.buildEvidencePackageArtifacts()` 生成包体
  - 成功：更新 `AuditEvidencePackage.status → READY`，写入 `GENERATION_COMPLETED`
  - 失败：更新 `AuditEvidencePackage.status → FAILED`，写入 `GENERATION_FAILED`

**审批拒绝**：
- `ApprovalCase.status → REJECTED`
- 系统监听 `ApprovalEvents.REJECTED`，更新 `AuditEvidencePackage.status → REJECTED`
- 写入 `APPROVAL_DECLINED` 审计事件

**取消**（Maker 或 SUPER_ADMIN 触发）：
- `ApprovalCase.status → CANCELLED`
- 系统监听 `ApprovalEvents.CANCELLED`，更新 `AuditEvidencePackage.status → CANCELLED`
- 写入 `APPROVAL_CANCELLED` 审计事件

**超时**（24h 无决策）：
- `ApprovalCase.status → EXPIRED`
- 系统监听 `ApprovalEvents.EXPIRED`，更新 `AuditEvidencePackage.status → EXPIRED`
- 不产生额外审计事件（审批超时属于系统自动行为，已在通用审批层记录）

### 4.4 Step 3 — 下载证据包

**触发入口**：Audit Center → Evidence Packages → 找到 `READY` 状态的包 → 下载

**系统校验**（下载前）：
1. `AuditEvidencePackage.status` 必须为 `READY`（否则返回 400）
2. 关联 `ApprovalCase` 必须已 `APPROVED`（否则返回 403）
3. `packageBody` 不为空（否则返回 500）

**响应**：返回包体内容（JSON），同时写入 `PACKAGE_DOWNLOADED` 审计事件。每次下载独立写入事件（`requestId` 含时间戳，避免幂等碰撞）。

## 6. 审计事件序列

### 6.1 正常流程（申请→审批通过→生成成功→下载）

所有事件共享同一 `traceId`，`workflowType = AUDIT_EVIDENCE_EXPORT`。

```
Trace: AUDIT_EVIDENCE_EXPORT / {traceId}
Entity: AuditEvidencePackage / {packageNo}

① EXPORT_REQUESTED
   - triggerType: EVIDENCE_EXPORT
   - actor: Maker (COMPLIANCE_OFFICER)
   - result: SUCCESS
   - metadata: { dateRangeFrom, dateRangeTo, itemCount }
   - subjectNos: [APPROVAL_CASE/{approvalNo}, AUDIT_EVIDENCE_PACKAGE/{packageNo}]

② APPROVAL_GRANTED
   - triggerType: EVIDENCE_EXPORT
   - actor: Checker (MLRO)
   - result: SUCCESS
   - metadata: { dateRangeFrom, dateRangeTo, caseId }
   - subjectNos: [APPROVAL_CASE/{approvalNo}, AUDIT_EVIDENCE_PACKAGE/{packageNo}]

③ GENERATION_COMPLETED
   - triggerType: EVIDENCE_EXPORT
   - actor: Maker（以申请人身份执行打包）
   - result: SUCCESS
   - metadata: { fileSize, fileCount }
   - subjectNos: 无（系统生成节点）

④ PACKAGE_DOWNLOADED
   - triggerType: EVIDENCE_EXPORT
   - actor: 执行下载的用户
   - result: SUCCESS
   - subjectNos: [APPROVAL_CASE/{approvalNo}, AUDIT_EVIDENCE_PACKAGE/{packageNo}]
```

### 6.2 审批拒绝流程

```
① EXPORT_REQUESTED      (同上)

② APPROVAL_DECLINED
   - actor: Checker
   - result: REJECTED
   - metadata: { dateRangeFrom, dateRangeTo, caseId }
```

### 6.3 取消流程

```
① EXPORT_REQUESTED      (同上)

② APPROVAL_CANCELLED
   - actor: 取消人（Maker 或 SUPER_ADMIN）
   - result: SUCCESS
   - metadata: { caseId }
```

### 6.4 生成失败流程

```
① EXPORT_REQUESTED      (同上)
② APPROVAL_GRANTED      (同上)

③ GENERATION_FAILED
   - actor: Maker（打包执行人）
   - result: FAILED
   - metadata: { failureReason: "错误信息" }
```

### 6.5 全 Action 值一览

| Action 常量（`AuditGovernanceActions.AUDIT_EVIDENCE_EXPORT.*`） | 值 | 触发时机 |
|---|---|---|
| `EXPORT_REQUESTED` | `'EXPORT_REQUESTED'` | 申请提交成功 |
| `APPROVAL_GRANTED` | `'APPROVAL_GRANTED'` | Checker 审批通过 |
| `APPROVAL_DECLINED` | `'APPROVAL_DECLINED'` | Checker 审批拒绝 |
| `APPROVAL_CANCELLED` | `'APPROVAL_CANCELLED'` | 申请被取消 |
| `GENERATION_COMPLETED` | `'GENERATION_COMPLETED'` | 包体生成成功 |
| `GENERATION_FAILED` | `'GENERATION_FAILED'` | 包体生成失败 |
| `PACKAGE_DOWNLOADED` | `'PACKAGE_DOWNLOADED'` | 包文件被下载 |

> **架构说明（Plan B）**：以上全部审计事件由 `AuditEvidenceExportApprovalService` **独占写入**，`ApprovalsService` 对 `AUDIT_EVIDENCE_EXPORT` workflowType 不写任何通用审批事件，避免重复。

## 7. API 规格

### 7.1 创建导出申请

```
POST /admin/audit/evidence-packages
Content-Type: application/json
Authorization: Bearer {token}

Request Body:
{
  "selectedEventIds": ["uuid-1", "uuid-2", ...],  // 必填，选中的审计事件 ID 列表
  "mode": "SELECTION",                             // 可选，默认 SELECTION
  "startAt": "2026-01-01T00:00:00Z",              // 可选，辅助 manifest 记录
  "endAt": "2026-04-29T23:59:59Z",                // 可选
  "maxItems": 1000,                                // 可选，上限 5000
  "includeRecords": true                           // 可选，是否在包体中包含明细，默认 true
}

Response 201:
{
  "id": "uuid",
  "packageNo": "AEP-20260429-0001",
  "status": "PENDING_APPROVAL",
  "approvalCaseId": "uuid",
  "approvalCaseNo": "APR-20260429-0001",
  "itemCount": 42,
  "exportMode": "SELECTION",
  "createdAt": "2026-04-29T14:00:00.000Z"
}
```

```
GET /admin/audit/evidence-packages/:id/download

- AuditEvidencePackage.status === 'READY'
- 关联 ApprovalCase.status === 'APPROVED'
```

## 9. 错误场景与边界条件

| 场景 | 系统行为 | HTTP 状态码 |
|---|---|---|
| 提交时 `selectedEventIds` 为空 | 拒绝创建，返回校验错误 | 400 |
| `selectedEventIds` 中含不存在的事件 ID | 拒绝创建，返回校验错误 | 422 |
| 同一用户对同一 packageNo 重复提交 | 幂等处理，返回已存在的申请 | 200/201 |
| Maker 本人尝试审批自己的申请 | SoD 拒绝，返回 403 | 403 |
| 非 MLRO 角色调用审批接口 | 权限拒绝，返回 403 | 403 |
| 下载 `PENDING_APPROVAL` 状态的包 | 返回 400，说明包尚未就绪 | 400 |
| 下载 `FAILED` 状态的包 | 返回 400，说明生成失败需重新申请 | 400 |
| 审批通过后打包抛出异常 | 包状态变 `FAILED`，写 `GENERATION_FAILED` 审计事件，`ApprovalCase.executionStatus = EXECUTION_FAILED` | 异步，不直接返回 HTTP 错误 |
| 证据包已软删除后尝试访问 | 返回 404 | 404 |
| 超过 24h 未审批 | 定时任务将 ApprovalCase 变为 `EXPIRED`，包状态变 `EXPIRED` | 异步 |

## 10. 验收标准（Acceptance Criteria）

### 10.1 功能验收

- [ ] Maker 提交申请后，`AuditEvidencePackage.status = PENDING_APPROVAL`，`ApprovalCase.status = PENDING`
- [ ] 审计日志中存在 `EXPORT_REQUESTED` 事件，actor 为 Maker，metadata 含 `itemCount`
- [ ] Checker 审批通过后，30 秒内 `AuditEvidencePackage.status` 变为 `READY` 或 `FAILED`
- [ ] `READY` 状态的包可以通过 GET /:id/download 下载，响应包含 `records` 和 `digest`
- [ ] 下载后审计日志中存在 `PACKAGE_DOWNLOADED` 事件，actor 为实际下载人
- [ ] Maker 自审触发 SoD 拒绝，返回 403

### 10.2 审计完整性验收

- [ ] 正常流程完成后，`audit_log_events` 中存在 4 条事件：`EXPORT_REQUESTED`、`APPROVAL_GRANTED`、`GENERATION_COMPLETED`、`PACKAGE_DOWNLOADED`
- [ ] 所有 4 条事件共享同一 `traceId`
- [ ] 所有事件的 `workflowType = AUDIT_EVIDENCE_EXPORT`
- [ ] `EXPORT_REQUESTED` 和 `APPROVAL_GRANTED` 的 `subjectNos` 包含 packageNo 和 approvalNo 两条
- [ ] 无重复审计事件（`ApprovalCase` 通用事件 `APPROVAL_SUBMITTED` 等不出现在 C5 的 traceId 下）

### 10.3 数据完整性验收

- [ ] `AuditEvidencePackage.digest` 与包体内容的 SHA256 一致
- [ ] `filterSnapshot` 和 `selectedEventIdsSnapshot` 在申请创建后不可修改
- [ ] 证据包软删除后，`packageBody` 数据仍保留在 DB 中

### 11.2 关键设计决策

**Plan B 独占审计写入**：`AuditEvidenceExportApprovalService` 是 C5 workflow 的唯一审计写入者。`ApprovalsService` 通过 `hasDedicatedAuditService('AUDIT_EVIDENCE_EXPORT')` 返回 `true` 来跳过通用审批事件的写入。这避免了通用事件（`APPROVAL_SUBMITTED`、`APPROVAL_APPROVED` 等）与 C5 语义事件（`APPROVAL_GRANTED` 等）的重复。

**事件监听驱动**：审批通过/拒绝/取消/超时后的处理，通过 `@OnEvent(ApprovalEvents.APPROVED/REJECTED/CANCELLED/EXPIRED)` 解耦。`AuditEvidenceExportApprovalService` 监听事件并执行对应的状态更新和审计记录。

**两阶段包体**：证据包创建时只有 manifest skeleton，审批通过后异步填充 `packageBody`。`packageBody = null` 是合法的 `PENDING_APPROVAL` 状态，下载接口会拒绝非 `READY` 状态的访问。
