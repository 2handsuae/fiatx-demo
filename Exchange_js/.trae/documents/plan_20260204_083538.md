# Implementation Plan: Payin Owner Mapping & Timeline Visualization

## 1. Backend: Link Payin to Customer & Track Status History
We will modify `src/modules/asset-treasury/payins/payins.service.ts` to implement two key features:

### A. Auto-associate Customer via Wallet
- **Logic**: When creating a Payin (e.g., in `simulate`), we will look up the target `Wallet`.
- **Mapping**: If the wallet's `ownerType` is `'CUSTOMER'`, we will extract the `ownerId` and save it to the `Payin.ownerId` field.
- **Goal**: This establishes the database relationship required to trace a Payin back to a Customer.

### B. Maintain Status History (JSON)
- **Initialization**: On creation, initialize `statusHistory` with the first event (e.g., `DETECTED`).
- **Update**: In `updateStatus`, instead of just changing the status column, we will:
  1. Parse the existing `statusHistory`.
  2. Append a new entry: `{ status, changedAt, reason, operatorId }`.
  3. Save the updated JSON string back to the database.

## 2. Frontend: Visual Status Timeline
We will refactor `admin-web/src/pages/PayinDetail.tsx` to replace the raw JSON dump with a polished Timeline component.

### Timeline Component Design
- **Visuals**: A vertical timeline with connected dots/nodes.
- **Content**:
  - **Left/Top**: Timestamp of the change.
  - **Node**: Icon indicating the status (e.g., Check for Cleared, Alert for Failed).
  - **Right/Bottom**: Status label, Operator info, and Reason/Notes.
- **Sorting**: Ensure events are sorted by time (newest on top or bottom as appropriate).
- **Features**: Responsive design that works on mobile and desktop.

## Verification
- **Backend**: Trigger a simulated Payin and verify `ownerId` is populated and `statusHistory` is initialized. Perform status changes and verify history grows.
- **Frontend**: View the Payin Detail page and confirm the Timeline renders correctly and matches the history data.
