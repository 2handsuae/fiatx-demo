# 战役丙波二「讲清楚、给凭据」骨架

> 总纲：`2026-09-30-campaign-c-outreach-disclosure-charter.md`（§2 波二行）｜ 骨架立于 2026-10-01（波一收尾同批）；展开 = 新会话读总纲+本骨架后跟业主脑暴，本骨架只登已定事实与待定岔口，不代做。

## 承接上一波

波一「让客户听得见」（16 发信点 / 消息中心 / gateway 复活 / 三页信号刷新）已合 main，`2026-09-30-campaign-c-wave1-notifications-spec.md`（含"执行订正"节）为现状真相；以下为波一收尾时坐实的偏差与新事实，波二立 spec 时直接继承，不再重新论证：

1. **兑换域的通知接线落点是 workflow 层 + SLA 服务的事务后置调用，不是状态落地处同步直调**——T7 首版把 `NotificationsService` 调用放进 `markStatus` 所在的 `$transaction` 回调内，因该服务走独立 Prisma 连接写 `customer_notifications`，SQLite 单写者下被外层未提交事务自锁到 5000ms 超时、外层事务回滚但通知已落库发出，还被 SLA sweep（`@Cron` 每 30 秒）反复重试同一死路、每轮再发一条重复假通知（完整复现记录见 `BACKLOG.md:106`、根因报告 `task-10-report.md`）。修法：私有方法在对应 `$transaction` resolve **之后**调用，兑换域最终落到 `SwapWorkflowService` 8 处调用点 + `SwapSlaService` 超时拒单 1 处，共 9 个事务后置调用点。**判例**：任何"横切服务挂在状态迁移点上"的新接线，若该服务走独立数据库连接，都要先问"这次调用是否可能还在外层事务里"——波二若有报价/确认单落库挂在兑换成交事件上，同样要过这道检查。
2. **FROZEN 收敛口径订正**：`toCustomerSwapStatus(FROZEN)` = `'COMPLIANCE_PENDING'`，不是字面的 `PROCESSING`；FROZEN 唯一入边来自 `COMPLIANCE_PENDING --FREEZE-->`，两端收敛值恒等——冻结落地前后连信号/通知的判据都不成立（零通知、零信号），这不是遗漏是设计意图。波一 spec §1 原文"处理中"是口语措辞，波二若引用同一收敛函数的文字描述，直接写字面状态码，不要沿用"处理中"这类可能被误读成 `PROCESSING` 的口语。
3. **客户端新增可复用地基**：铃铛 + `/messages` + 四类深链（按 `relatedOrderType` 路由到 DEPOSIT/WITHDRAW/SWAP/COMPLAINT 详情）已上线；模板登记处 `notification-templates.constant.ts`（写死代码、无编辑面，词表式）这一模式——波二"成交前三句话"固定文案、"风险提示文案"如果也走"写死代码集中登记"的形态，可直接抄这个模式，不必重新设计登记处的形态问题。
4. **decisions:11 缓办债已清（本次核实）**：三域客户面响应均经各自 `toCustomer*Status` 收敛后下发，充值侧为白名单反转设计（`deposit-transactions.service.ts:86-118`）。波二动确认单/披露文案时不必再把这条缓办债当作待议项摆上桌。
5. **条款同意落库（岔口 7）仍是前端闸，未落地**：现状 `acceptTerms` 纯前端校验（`CustomerRegister.tsx:15-16` 自认，`src`/`prisma` 零命中持久化），波一未碰这块——波二骨架岔口 7 承接的"补谁/何时/哪个版本落库+审计"仍是波二 T 对象，不是已完成项。
6. **搜索范围判例**：波一执行中发现，按目录局部 grep 找调用点容易漏掉"邻居模块"——`toCustomerSwapStatus` 的调用方分布在 `swap-transactions.service.ts`（本体）、`swap-workflow.service.ts`、`swap-sla.service.ts` 三个不同文件，只搜本体文件会漏掉后两处的 9 个通知调用点。波二若要排查某个收敛函数/状态判据的全部调用面，搜索范围要扩到同域的 workflow/sla/webhook 等平行服务文件，不能只搜"看起来最相关"的那一个。

## 已定事实（继承自总纲 §1/§2，波二立 spec 时直接引用）

1. **范围三件**：成交前三句身份话（本金身份/定价方法=市场价+点差/利益冲突）固定文案进确认弹窗；成交后不可变成交确认单（成交时刻价/费/时间定格）；充值/提现页风险提示文案。
2. **条款同意落库**：版本 + 时间戳 + 审计（岔口 7，见上"承接"第 5 点，尚未落地）。
3. **不做**：报价成交链任何行为改动（纯展示+快照+落库）；best-exec 比价闸（属搁置总纲波二，不捞）。
4. **模板同样写死代码**（同波一模式，见上"承接"第 3 点）。

## 待定岔口（展开脑暴用，指回总纲 §3 波二行）

1. 冷静期做不做。
2. 确认单要不要覆盖充值/提现（参照系只点名兑换）。
3. 风险提示文案的位置与密度。
4. 条款同意落库的审计形态——是否需要专门审计码，还是复用既有 `CUSTOMER_*` 名册。
5. 确认单与通知本体的关系——"确认单已出"要不要吃波一的消息中心（非硬依赖，按总纲 §2 波三行同款措辞，波二若想吃可以直接复用波一的 `NotificationsService.send()` 单一写点）。
