# 决策日志（交付摘选）——保护「看起来傻、其实是刻意」的设计

> **权威真身是 `doc-final/decisions.md`**（全量、只追加、不改不删）。本文件是给接手开发的摘选：只挑**重做时最可能被好心「优化」掉**的决策，每条给结论与理由，细节按日期回真身查。两处不一致以 `decisions.md` 为准。
> 读法：看到 demo 里一个「不合理」的设计，先来这里查有没有它的名字；没有再去问产品，**不要直接改**。

- **D-1 逐腿实时记账，没有日终轧差**。曾有内部转账 / EOD 轧差 / 归集 cron 整套方案，已删——账要时刻对得上，对账才有锚。（2026-06-25）
- **D-2 费腿独立，不并进净额腿**。合并省事；否——费腿独立是实时 1:1 对账的锚，塌了对不上账。客户阅读体验交给展示层聚合。（2026-07-07）
- **D-3 Travel Rule 不建独立交换实体表**。TR 数据锚在订单字段＋无状态应答器，Sumsub 存真身——不自建合规审核台、不为过渡设计立表。（2026-07-14）
- **D-4 TR 阈值按币种写死在代码里，不做管理台可配**。监管数值的改动应走发版评审，不该是运营旋钮。（2026-07-31）
- **D-5 COA 终盘 9 码，三条永久否决**：暂扣场景不拆科目、点差不单独记账、不按费种立户。COA 为系统服务，财务需求走对钩视图，不预留号段。（2026-08-13）
- **D-6 合规执行由 Sumsub 承接**。内部合规信号管道（compliance-alerts / incidents 信号版 / RiskDecisionOrchestrator）已删——平台是接入方，不是审核台。（[合规承接]）
- **D-7 配置变更走标准 maker/checker 审批**，不建 config-as-code 发布流水线。（[配置治理]）
- **D-8 SLA 一律按「进入状态」计时**，与 onHold 解绑；硬破线推状态、软破线只置标记——旧挂回调机制从未真正跑起来。（2026-08-21）
- **D-9 资金单的判据是「有没有在途要追」**，不是「有没有物理转账」。银行利息、账管费这类事后追认的既成事实只落账本分录、不建资金单。（2026-08-28）
- **D-10 客户侧「公司承担」没有账面捷径**：客户钱包与公司钱包是两组物理钱包，公司认损＝认损调账＋真金白银补款划转两步，不许一笔账面冲平了事。（2026-08-28 / 2026-09-05）
- **D-11 调账单不得补记真实发生的客户资金流**。外面真有钱进出而我方未记的，回对应业务域把流程补跑——凭空调账＝绕过 KYT 与合规闸的后门。（2026-08-28）
- **D-12 对账处置没有「对方错」这一档**。外部资料是权威，一切不平只有：我方错 / 我方缺 / 时机没到。（2026-09-01）
- **D-13 豁免与容差不做**：本系统与服务商精度一致，通向豁免的成因不存在。立场是「一分不差，一分也追」。（2026-09-02）
- **D-14 上币走开发流程，运营只开启/暂停；定价不建管理面**。合约地址填错一个字钱就没了，这类事实走代码评审与发布记录，不做运营页面。（2026-09-03）
- **D-15 退汇只有法币**。链上转账最终不可逆，「像退汇」的事各有其名（重组＝假信号入账、未确认＝已记未执行、对方打回＝新进账走补录）。（2026-09-03）
- **D-16 充值不设累计限额门**。充值是被动入金，累计门只管出金与交易。（2026-09-05）
- **D-17 费率即改即生效（30 日历日生效闸不做）；选档引擎只减免不加价（cheapest）**。（2026-09-05）
- **D-18 客户档位单向升不降**：降级的天然触发器（定期风评、材料时效巡查）均已裁掉；合规恶化的表达是限制条子（更快更狠）。升档不设次数限制与冷却期。（2026-09-07）
- **D-19 提现报价 TTL 远长于兑换报价，两域刻意不对称**：提现锁的是费用快照、兑换锁的是汇率（RFQ 行业惯例）。不要「统一」。（2026-09-09）
- **D-20 swap FROZEN 是押锁不放的中间态，不是终态**；三域客户被冻后新单**允许创建、创建即冻**——中性报错拦截本身就是通风报信。（2026-09-14）
- **D-21 事故登记零账务**。事故是治理件（谁知道、何时升级、上报没有、谁结案），善后走既有原语（补录/认领/认损/补款），追索只登记不入账。（2026-09-06）
- **D-22 对账不再加复核签核层**：动钱处置本来就是金库开单 → CFO 批两人四眼；推单与挂起维持一人完成（挂起零账务、推单不直写账）。（2026-09-19）
- **D-23 业务日＝迪拜自然日（恒定 UTC+4），不取「银行 17/18 点 COB」变体**——多一个魔法数字，演示一句话讲不清。（2026-09-21）
- **D-24 客户通知三原则：持久物先于信号、`$transaction` resolve 后调、服务边界吞错**——消息行+审计是真相，socket 信号只是加速器；事务内跨连接写通知表在 SQLite 单写者下自锁回滚（实证 49 条假通知）。（2026-10-01）
- **D-25 客户自助「标已读」不入审计**——铁律①作用域是 operator 的持久化动作，客户读位标记不是业务动作；客户面业务动作（建单等）照旧留痕。（2026-10-01）
- **D-26 成交确认单三性：一单一张、只写一次、SUCCESS 事务后置出具**——`trade_confirmations` 以 swapNo 唯一约束结构保证一单一张；服务零 update 入口；出具挂状态变更 `$transaction` resolve 后（先落单 → `CONFIRMATION_ISSUED` 审计 → 再发通知，D-24 三原则的延伸）；仅收敛态 SUCCESS 出具，冻结/拒绝零出具（tipping-off）。对外用业务键 `CNF+12位`。（2026-10-02）
- **D-27 客户协议三性：版本正文代码登记且不可变、同意只追加、30 天通知期锚批准时刻；未同意只拦充值与兑换、放行提现且显式拒绝**——版本行只存状态与生效日、正文住代码登记处（改字 = 新增一版，不是改库）；同意台账 append-only，先拒后同意各一行，判定取"对**当前生效版**是否有 ACCEPTED"；监管 30 天通知期（VARA MC II.A.7）锚批准时刻，批准时复核、不设独立"通知时间"；拦 DEPOSIT/SWAP 放 WITHDRAW（不锁客户的钱），拒绝显式 `AGREEMENT_NOT_ACCEPTED`、不走中性话术；与费率表零联动。版本键 `v1`/`v2` **刻意不走单号惯例**（版本非单据、总量个位数、对客展示物）——不是漏用 `generateReferenceNo`。（2026-10-02）
