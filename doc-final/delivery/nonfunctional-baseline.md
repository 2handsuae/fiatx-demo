# 非功能底线——专写 demo 里看不见的

> 判据：**demo 里跑不出来、但生产没有就出事的，才写在这里**；demo 能演示的（状态机、审批、记账、审计）一个字不写。
> 背景：demo 是演示系统，**明令不做技术兜底**（幂等/去重/重试/并发锁/权限加固/防御校验，见仓库 `CLAUDE.md` §2-§3），并假设单人顺序操作、外部系统准时回调且只回一次、管理员善意。**这些假设生产一条都不成立**，以下每条都是下限，不是建议。
> 已知实例的逐条登记册（含文件位置与实证复现）在 `doc-final/PRODUCTION-NOTES.md`，随包带出——生产化从那里逐条起步。

1. **Webhook 幂等**：同一外部事件送达两次，不得二次记账、二次推状态。demo 假设「只回一次」，无去重键防线。
2. **并发与竞态**：同一单据的并发操作必须防重。demo 的审批落地链是事件驱动的最终一致（`approve()` 返回时级联可能仍在途、无重试队列），生产要么真同步、要么带重试与死信处理。
3. **事务边界**：「建资金单 ＋ 账本锁定 ＋ 状态落库」必须原子提交或带补偿。demo 部分弧是裸序执行，失败会留孤儿资金单。
4. **外部调用姿势**：先落库再外调；外调失败要有重试与人工 repair 出口。demo 里 TB 记账失败只记一条审计然后卡住，无修复面。
5. **密钥与认证**：密钥不进代码、不设字面量回落（demo 的 JWT_SECRET 有硬编码回落）；SUPER_ADMIN 的 SoD bypass 上线前必须移除；令牌要有吊销/失效机制（demo 是无状态 JWT，可多处同时登录）。
6. **管理 API 硬化**：所有 admin 端点强制管理员断言且 fail-closed。demo 的权限守卫对非 ADMIN token 存在 fail-open 面（属演示假设「管理员善意」，已逐条登记）。
7. **响应白名单**：对外响应一律白名单字段。demo 存在把 `passwordHash`、调查性字段随 include 带出的实例（在册）。
8. **输入校验**：边界防御性校验 demo 明令不做，生产按正常标准补齐。
9. **审计不可篡改**：库级禁止 UPDATE/DELETE、可信时钟（UTC+NTP）、digest 取未脱敏原文——五条非字段约定 demo 未实现（在册）。
10. **链上现实**：txHash 唯一约束、按链确认数、区块重组回退、合约执行失败交易过滤——demo 的链是遥控的，这些现实一个都没有。
11. **迁移策略**：demo 教义是「数据随时重铺」，schema 改动直接按终态做、零兼容层；生产要真迁移与回滚方案。
12. **可观测性**：demo 的静默降级点（如未注册币种阈值只 `logger.warn`）生产必须接告警；关键不变量（恒等式、负余额）要有持续监控，不能只靠演示前手跑 verify 脚本。
13. **通知投递语义**：demo 的客户通知是尽力而为——站内消息+`EMAIL_SIMULATED` 落库留痕（不真发），发送失败整体吞错、无重试、无已达回执；持久物（`customer_notifications` 行+`NOTIFICATION_SENT` 审计）是唯一真相，socket 信号只是加速器。生产要真实投递通道（email/push/webhook）、重试与退信处理、已达追踪与失败告警。

工程质量整体以 demo 为耻（见根 README 四刀声明第一刀）：demo 的错误处理、测试姿势、安全姿势都不构成标准。
