## 0. 一句话定位

**账本是整个系统的事实层，而且它按「钱在哪儿」记。** TigerBeetle 复式记账是余额的唯一真相——数据库里没有"余额字段"，只有凭证与流水投影。每笔交易就地逐腿记账（实时 1:1），没有日终轧差、没有延迟结算；每个真实钱包 / 账号在账本里恰好是一个**现金户**，所以对账能拿「一个现金户」去比「一张托管方对账单」。

## 1. 业务叙事

最重要的一件事：**余额不是一个被改来改去的数字，是账本里借贷相抵的结果。** 想让客户余额变，唯一的办法是记一笔账——这就是"凭空造钱"在这个系统里做不到的原因。

**13 个科目码，分五类讲完家底。**

- **资产·现金类（每个钱包一户）**：码 1 客户现金（客户的 vIBAN / 充值地址里的钱）、码 50 公司现金（公司七个钱包行里的钱：运营 AED / USDT、结算 AED、手续费 AED / USDT、LP 前厅 AED / USDT）。户名 = `类名 · 钱包名`，例 `Company Cash · Company Operations · AED_ZAND`、`Client Cash · CU2601012635 · vIBAN`。
- **资产·非现金借方户**：码 2 托管短缺待补（每个客户钱包一户，只在短缺期间有余额——托管方少了客户的钱、公司认下待补的那一截）；码 51 应收 LP 交货（每 LP 每币种一户——钱已付给 LP、货还没到的那一截）。它们是借方户但**不是现金户**，不与物理钱包一比一。
- **负债·客户本**：码 100 客户应付（欠客户的，每客户每币种）、码 101 客户暂扣（进了门还没放行的）。码 150 应付供应商列在表里**但不开户**（不做月度计提）。
- **权益与收入**：码 200 公司权益（每币种一户：本钱 + 交易净额，注资贷此户、兑换以它为对手盘）；210 / 211 / 212 三个收入户（兑换费 / 提现费 / 其他——没收入公司的钱归"其他"，与服务费隔离）。
- **开支（借方户，每币种一户）**：300 银行与托管费用、301 对账核销损失、302 其他开支。

**类是代码定义的，户随钱包登记自动开**（业主原则：科目表为系统服务，财务口径走报表视图，不预留号段）。开户粒度与时机：

| 类 | 粒度 | 谁在什么时候开 |
|---|---|---|
| 1 / 2 | 每个客户钱包 | 钱包行建出来（`WalletCashAccountService.ensureForWallet`）一次开 1 + 2 |
| 50 | 每个公司钱包 | 同上（种子七行平台钱包都开现金户） |
| 51 | 每 LP 每币种 | LP 档案走到 ACTIVE（审批批准 / 金库复活，`LpReceivableAccountService.ensureForLp`） |
| 100 / 101 | 每客户每币种 | 客户入驻激活 |
| 200 / 210–212 / 300–302 | 每币种一户（归属 SYSTEM） | 上币 |

**两条恒等式是天平，按币种各自守恒，随时可验。** 客户本：Σ(1 客户现金) + Σ(2 托管短缺待补) = Σ(100 客户应付) + Σ(101 客户暂扣)；公司本：Σ(50) + Σ(51) + Σ(300..302) = Σ(200) + Σ(210..212) + Σ(150)。客户钱包里的钱不够覆盖应付 + 暂扣的那一截，就是码 2 上挂着的数。

**恒等式有个盲区，负余额断言补上。** 两侧同增同减的错账（凭空造余额、超额划扣）恒等式看不见——正负相消照样全绿。所以账本在开户时就按类设标志位：借方户禁「贷超借」、贷方户禁「借超贷」，**记成负数的那笔账本身会被 TigerBeetle 拒掉**；校验器再遍历每个户做第二道：**任何户余额为负即失败**。

**公司权益 ≥ 公司现金·运营，恒成立。** 手续费钱包的钱扫进运营户之后，运营户的钱比公司权益多，卖光运营户就会把权益减成负数。所以「手续费户 → 运营户」的调拨腿确认时同步把等额收入结转进公司权益（码 90）；谁给公司权益加一条不经现金的借方分录，这个保证就破了。

**先锁后落。** 提现和充值的处置弧（没收 / 退回 / 上缴）都走两阶段：先锁定（挂起中的钱两边都看得见但谁也用不了）→ 结算落定或作废解锁。客户"可用余额" = 账面余额 − 锁定中金额。

**科目也有生死。** 旧的手续费 / 罚没两户（COA v2）、结算中转与 LP 前厅两个独立科目（COA v3）都已退役：后两者作为科目退役、作为现金户存续（钱包 F_SET / F_LIQ 照旧，钱住在各自的公司现金户里）。退役名进防回归黑名单，demo 数据随时重铺，不留迁移脚本、不留双写。

**永久否决三条（COA v2 起维持）**：暂扣场景不拆科目、点差不单独记账、不按费种立户。

## 2. 不变量（本域没有状态机，只有天平）

| 不变量 | 口径 |
|---|---|
| 客户侧恒等 | Σ(1) + Σ(2) = Σ(100) + Σ(101)，按币种 |
| 公司侧恒等 | Σ(50) + Σ(51) + Σ(300..302) = Σ(200) + Σ(210..212)（+ Σ(150)，不开户故为 0），按币种 |
| 无负余额 | 全部户：借方户（1 / 2 / 50 / 51 / 300–302）`credits_must_not_exceed_debits`，贷方户（100–212）`debits_must_not_exceed_credits`；余额按借贷方向算出 ≥ 0 |
| 公司权益 ≥ 公司现金·运营 | 靠扫费同额结转钉住；不是校验器断言，是上面两条加记账规则的推论 |
| 码 2 托管短缺待补 | 归属 WALLET，**不是现金户**（`CASH_TB_CODES` 只含 1 / 50），对账不把它的流水当钱包流水（投影器码 2 流水不带 `walletRef`）；认损补缺单批准时借 2 / 贷 1（码 91）记短缺，补缺腿确认时借 1 / 贷 2（码 83）冲平；客户应付全程不动 |
| 码 51 应收 LP 交货 | 归属 LP，不是现金户；LP 兑换单卖出腿确认时借 51 / 贷 200（码 88），LP 到货时贷 51（码 85）冲平 |
| NLA（监管净流动资产）口径一句 | 公司现金里**运营、手续费、LP 前厅三个钱包**的 AED + USDT（USDT 按钉住汇率折 AED）；结算钱包与应收 LP 不算；详见 `company-funds.md` §NLA |
| 账户唯一 | (科目码, 币种, 归属类型, 归属人) 四元组唯一 |
| 转账码 | 1–91 一经分配不可改号；段落索引见下，**每个码的借 / 贷 / eventCode 以 `reference/coa-v3.md` §2 为准** |
| 验证入口 | `verify:coa`——两恒等式 + 负余额断言，秒级，动钱任务收尾闸⑦ |

转账码段落索引：1–9 充值（到账 / 放行 / 没收 / 退回 / 上缴）｜10–17 提现（锁定 / 落账 / 作废 / 费 / 退汇）｜20–21 上缴作废与入账追回（21 挂起）｜30–38 兑换｜70 注资｜80 平账调账｜81–83 内部划转（83 按用途分两种贷方）｜84–86 LP 兑换｜87 供应商付款｜88 应收 LP｜89 公司调拨｜90 扫费结转｜91 认损记短缺。

## 3. 决策点与角色

- **科目增删 = 代码变更**，走发版评审，不是管理台操作；**手动建账**仅剩一个 admin 兜底端点（带审计）
- **记账失败 = 流程失败**（铁律 §5.5）：工作流同步直调记账，失败则业务状态不得推进——绝不把记账挂到事件上异步补
- 账本读面三页三权限分治：账户（实时余额）/ 凭证 / 流水（含每行过账后余额快照），只读为主；账户页可按 Owner = LP 过滤，码过滤含 2 / 51
- 账户页与流水页显示户名：现金户读开户时写好的户名（`类名 · 钱包名`），其余户「一码一名」（`tb-account-codes.constant.ts` 的 `TB_ACCOUNT_NAMES`，英文名）；前端不得另造 code → 名字映射

## 4. 演示脚本（账本视角，贯穿各幕）

1. 第三幕充值入账后 → 账本流水页看两步分录：钱到账记在**客户现金·该客户钱包**，放行后才变成客户应付；每行"过账后余额"
2. 第四幕兑换成功后 → 凭证页看四腿：钱在 客户现金 → 公司现金（结算 / 运营）→ 客户现金 之间一站一站走，收入户里兑换费到账
3. 第五幕提现锁定期 → 账户页看客户可用余额与锁定的差
4. 认损补缺（场景 16）→ 批准那一步先看到**托管短缺待补**户出现余额、客户现金同额减少、客户应付一分不动；补缺腿到账后短缺户归零
5. 扫费（场景 41）→ 手续费钱包的钱调拨进运营户，同一步三个收入户之一同额结转进公司权益
6. LP 兑换（场景 37）→ 卖出腿确认后**应收 LP**户出现余额，LP 到货后冲平，货落进 LP 前厅现金户，验收后转运营户
7. 第六幕开场 → 现场跑 `verify:coa` 全绿，讲两恒等式与负余额断言的分工
8. 任一凭证 → 点开看借贷双方科目、参考号、生效日——"每一分钱都有对手方"

## 5. 关键技术节点（≤30 行）

- 记账主 `accounting/tigerbeetle/accounting.service.ts`：`executeTransfer()`（实时单笔）｜ `executePendingTransfer()/postPendingTransfer()/voidPendingTransfer()`（两阶段；post/void 对"已处理"回执放行为幂等 no-op）｜ `getCustomerAvailableBalance()`（可用=posted−pending）｜ `resolveCashAccountId(walletId, ledger)`（全仓「钱包 → 现金户」唯一入口，对账读端与写端共用）｜ `assertWalletBalance(walletId, ledger, amountMinor)`（出钱前的余额闸，付款单 / 调拨单 / LP 兑换单 / 划转单共用）
