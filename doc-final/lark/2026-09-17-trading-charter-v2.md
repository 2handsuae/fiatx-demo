# **1. 这份文档是什么**

**一句话定位：**三条交易流程是三条平行的资金通道，共用同一副地基——两级门、资金单、账本、审计；它们的全部差异，源头只有一句话：**钱在这条流程里，什么时候还在我们手里**。本篇定这句话的三种答案，以及由它派生、无法从任何单篇推导出来的七条决议。

**本篇不写什么：**不写任何一条流程的完整状态机、闸门细节与验收标准——那是三篇订单文档各自的正文；不写 Sumsub 裁决的机制细节（裁决的四种形态、标签分类、总规则与偏离、人级处置）——那是《交易合规裁决》一篇。本篇只写**跨流程才成立**的东西：横向对照、共同规则、接缝归属。

**五篇的关系：**

| 文档 | 回答什么 | 读者从这里找什么 |
|-|-|-|
| **交易域总纲**（本篇） | 三条流程为什么长得不一样、共同规则是什么 | 横向对照；某条规则归谁管 |
| **交易合规裁决** | Sumsub 的裁决长什么样、标签怎么读、人怎么被处置 | 裁决与标签的定义、"三活一静"总规则、人级处置 |
| **充值 v2.0 / 提现 v2.0 / 兑换 v2.0** | 本域的状态机、闸门顺序、每条边的副作用、验收 | "这笔单现在该迁到哪、账怎么动" |

另有三篇《流程与内控说明》（充值 / 提现 / 兑换）是给财务合规与一线的操作口径，与本组 PRD 是两个层次：**PRD 写系统应该是什么样、怎么验；内控说明写人该怎么办、能说什么**。两者事实同源，用途不同。

# **2. 三条流程的分野：钱什么时候还在我们手里**

这是整个交易域唯一的心智模型。三条流程给出三种不同的答案，后面所有差异都是它的推论。

| 流程 | 钱的位置 | 控制的性质 |
|-|-|-|
| **充值** | 钱已经到了。链上落在我方托管地址、法币落进我方银行账户，**拒收是不存在的**——记录存在的那一刻，钱已在我方暂扣户里，只是还不在客户余额上 | 此后的每一个决定都是**放行**的决定，不是接受的决定 |
| **提现** | 钱要离开。一旦付出去就不可追回 | 所有控制都在争取**最后一个还能拦下**的时刻 |
| **兑换** | 钱从不离开托管。客户与平台自己对做，四条结算腿全部在我方控制的钱包之间移动，没有任何外部对手方 | 控制点前移：**批准发生在动钱之前**；一旦裁决放行，就没有中途叫停这回事 |

**由此得到三条流程各自的定律：**

- 充值——**每一个终局都必须回答"钱去哪了"**（决议一）。钱已在手，不放行就必须退回、留下或上缴，不存在"过期作废"。
- 提现——**门都开在出门之前，等待期里钱始终锁着**；任何非成功终局都必须全额解锁。
- 兑换——**批准先于动钱**。裁决放行之前，唯一的账务痕迹是出生锁（一对净额为零的挂账）：被拒即全额解锁，冻结则押锁等处置；而一旦执行开始，就没有中途叫停这回事，也没有失败终局。

# **3. 骨架：两级门**

三条流程共用同一副门架，分两级——**L1 是我方自己的条件判断，L2 是外部合规判断**。这两级的分工是交易域最重要的结构事实：L1 的答案全部来自我方数据库（客户状态、限制、限额、余额、报价、资产可用性），L2 的答案只能来自 Sumsub。

## **3.1 L1：十项闸，三域共用一份**

L1 是**一份代码、一个固定顺序、三域共用**的十项检查（`L1GateService`）。详情页按同一顺序渲染，三域一致：

| # | 检查项 | 问的是 | 充值 | 提现 | 兑换 |
|-|-|-|-|-|-|
| 1 | CUSTOMER_ELIGIBILITY | 客户生命周期是否 Active | ✓ | ✓ | ✓ |
| 2 | CUSTOMER_RESTRICTION | 客户是否被限制了本域能力 | ✓ | ✓ | ✓ |
| 3 | SINGLE_LIMIT | 单笔金额是否在上下限内 | ✓ | ✓ | ✓ |
| 4 | CUMULATIVE_LIMIT | 日 / 月累计额度是否够 | — | ✓ | ✓ |
| 5 | LARGE_APPROVAL | 是否触发大额人工签字 | — | ✓ | — |
| 6 | ACCOUNT_READINESS | 收 / 付账户是否就绪 | ✓ | ✓ | ✓ |
| 7 | BALANCE_SUFFICIENCY | 余额是否覆盖本笔 | — | ✓ | ✓ |
| 8 | QUOTE_VALIDITY | 报价是否存在且未过期 | — | ✓ | ✓ |
| 9 | TRADING_READINESS | 交易起始前置是否完成 | ✓ | ✓ | ✓ |
| 10 | ASSET_AVAILABILITY | 该资产是否被暂停 | ✓ | ✓ | ✓ |

**"—"是天然不适用，不是漏做**（业主 2026-08-22 逐条拍板）：充值的钱是进来的，所以没有余额问题、没有报价问题；累计额度对充值"拦不住"（钱已经到了），大额审批对充值"拒了也没用"（同上）。兑换刻意没有大额签字门，理由见决议三。

**三项自判自赢。**客户资格、客户限制、资产可用三项由 L1 服务亲自计算，**任何外部传入的同名结果一律丢弃**——这三项是安全关键判定，被覆盖成通过就等于闸门被静默绕过。

**L1 失败有稳定的机器可读原因码**，三域共用一份映射（生命周期不合格 / 能力被限制 / 低于下限 / 资产已暂停…），落在充值的挂起原因与提现兑换的拦截审计上——这是"被拦下也留痕"在交易域的落点。**限制项失败时，管理台 L1 快照直接给出具体因由与限制便签号**（RST 业务号，2026-09-14 起）——运营看得出"为什么被拦"；客户面继续保持藏，不区分限制的种类。

## **3.2 L2：唯一的合规入口**

L2 是 Sumsub 的交易监控裁决。设计规则一句话：**进入执行态的唯一通道是 L2 放行**——我方管理台没有任何"直接放行"按钮可以替代它。裁决的形态、标签分类与人级后果见《交易合规裁决》；三条流程**如何消费**同一个裁决，见各自的订单文档与本篇第 5 节的横向对照。

## **3.3 门的顺序与收单三态**

顺序本身是设计：**L1 在前、L2 在后**，且 L1 内部的顺序固定。推论——

- **L1 拒绝通常不产生订单**（提现 / 兑换：请求被当场拒，不锁钱、不消耗报价、无单可审），但有两个刻意的例外：
  - **充值**——钱已经到了，L1 不通过也必须建记录，只是把它挂起来等人处置；
  - **静默受限（SILENT）客户**——不拒、照常建单，**入库瞬间冻结**（"创建即冻"，见决议四）。持续的中性报错本身就是一种信号，折叠收单才是真正的不通风报信。**明示受限（DISCLOSED）客户维持中性拒绝**——横幅已经告知过他，报错不泄密。
- **合规判断永远不因为金额小而被跳过。**典型体现是充值：先过合规，再问"这笔是不是小到不值得放行"的商业问题，顺序不可颠倒。

# **4. 七条不容推导的决议**

## **决议一 · 每个终局必须回答"钱去哪了"**

终局不是流程的收尾标签，是对资金去向的陈述。这条规则的直接后果是**充值刻意没有"已拒绝"和"已过期"两种终局**——钱已经到账，"拒绝"和"过期"都回答不了钱在哪；不放行就必须退回、留下或上缴。同理，**兑换刻意没有"失败"终局**：裁决之前没有可失败的东西（拒绝就是拒绝），裁决之后的失败一律是临时状态（自动重试，重试用尽转人工旗标），因为"一笔已执行交易失败到一半"同样回答不了钱在哪。2026-09-13 起，兑换枚举里连"已失败 / 已冲正"这两个历史死值也已物理删除——枚举即状态，不再有"声明了但永远到不了"的值。

审查任何一个新终局的唯一提问：**它能不能一句话说清钱在谁手上。**

## **决议二 · 锁的三种做法**

| 流程 | 锁什么 | 什么时候锁 | 什么时候放 |
|-|-|-|-|
| 充值 | **不锁**——钱本来就在我方暂扣户，不在客户余额上 | — | 放行时从暂扣户转入客户余额 |
| 提现 | 本金 + 手续费 | 下单受理即锁 | 任何非成功**终局**全额解锁，一分不差；**冻结不解锁**——冻结不是终局 |
| 兑换 | 卖出侧全额 | 下单受理即锁 | 被拒（合规拒 / 超时拒 / 拒退批准）全额解锁，账本留一对净额为零的挂账记录作证据；**冻结不解锁** |

**不变量：锁定与解锁严格配对——配对的对象是"终局"。**每一个非成功终局伴随全额解锁，这是三域共同的验收项。**冻结不是终局**（2026-09-14 翻案，三域从此一致）：冻结期间锁保持原样、钱押着，解冻续审继续押，只有走到拒退 / 终局拒绝那一刻才放锁回余额。旧口径"兑换冻结即退余额、押人不押钱"作废——创建即冻落地后，"终态放钱"的前提已不存在。

## **决议三 · 限额是配置，签字门只配了提现一条**

三种门都是**配置行**（限额规则），不是硬编码，改动走配置治理。PRD 锁的是**维度与方向**，具体数字是出厂种子、运行时可调：

| 门 | 按什么维度配 | 出厂配置 |
|-|-|-|
| **单笔** SINGLE | 操作类型 × 资产 | 提现 / 兑换：五币种（BTC/ETH/USDT/AED/USD）各配上下限；充值：五币种**只配下限 100、无上限**（拒收不存在，上限拦不住已经到账的钱） |
| **累计** CUMULATIVE | 操作类型 × 交易档位 × 日/月 | 只配了提现与兑换 × BASIC/PREMIUM × 日/月（如 BASIC 提现日 5 万 / 月 50 万 AED，PREMIUM 兑换日 100 万 / 月 1000 万 AED）；充值无累计门 |
| **大额签字** LARGE_APPROVAL | 操作类型 | **只配了提现一行：200,000 AED** |

**大额门是 fail-closed 的：**金额无法折算成 AED 时（汇率不可得），一律强制转人工签字，而不是放行。签字链是高级管理层单步、48 小时、可撤回。

**兑换不设签字门——已裁定（业主 2026-09-12），不再重新评估。**两条理由：一是钱不会通过兑换离开托管，"金额大"本身不构成资金外流；二是兑换自身已有累计额度天花板，规模有上限。签字门与快是矛盾的——兑换是 30 秒的价格承诺，等人签字价格已经过期。

**⚠ 但有一条敞口要归位。**此前把"先大额兑换、再分拆提现"记作兑换侧的配对风险，**这个归类不准确**：分拆规避签字门是**提现自己的问题**，与兑换有没有门无关——客户账上本来就有余额时，一样可以分拆提走，兑换只是换了个币种。真正的问题是**签字线管单笔、累计额度管总量，两者正交**：分拆把每一笔压到线下，额度只管得住总量。这条列为待决问题 Q2，归属提现域。

## **决议四 · 制裁客户：单怎么收、人怎么冻**

**先立收单三态（业主 2026-09-14 拍板）。**客户身上挂着限制便签时，新的交易请求怎么收：

| 客户的限制形态 | 新单怎么收 | 为什么 |
|-|-|-|
| **静默限制**（SILENT，如制裁） | **照常建单，入库瞬间走既有冻结边转入冻结**（"创建即冻"） | 持续中性报错本身就是信号；折叠收单，客户看到的只是一笔普通的"处理中" |
| **明示限制**（DISCLOSED，如需补料） | 中性拒绝，不建单 | 客户已被横幅告知受限，报错不泄密 |
| 充值（任何限制形态） | 天然"收进来即冻"——钱到了就必须建记录，L1 直判入冻结 | 拒收不存在 |

配套的 **tipping-off 达标原则**：客户可见状态**跟着钱走**（钱押着 → 显示处理中；钱退回 → 显示终局），无声性靠**与普通业务结局不可区分**来保障，不靠"永远没有结局"——行业里调查扣审天然限时、终有结局，零出边的死冻结哪种制度都对不上。

**再立冻单与冻人的分界。**命中主体分四类场景标签——制裁·客户本人 / 制裁·对手方 / PEP·客户本人 / PEP·对手方：

| 标签 | 充值 / 提现 | 兑换 |
|-|-|-|
| 制裁·客户本人 | **先冻人、再冻单** | 冻单（中间态、押锁）+ 冻人 |
| 制裁·对手方 | 只冻单，**不冻人**（钱的另一端有问题，这笔不能走） | **不存在此场景**（兑换无外部对手方） |
| MLRO 冻结（处置标签） | 冻单，免审批，**不冻人** | 冻单，免审批，**不冻人** |
| PEP（任一主体） | 不冻结；按普通裁决路由 | 不冻结 |

**动人的条件只有一个：制裁·客户本人（2026-09-14 起三域统一）。**MLRO 冻结是调查扣审——冻单不冻人；无处置标签的普通拒绝只动单（充值因钱已入库落人工复核队列，是资金方向的物理差异，不是口径分歧）。曾经只在兑换域存在的"软线 / 硬线"自动便签已撤除——"充提向上补齐三档"一案按**向下拉平**消解。

**写入顺序是刻意的：先开客户限制、再冻订单。**两步之间若发生中断，留下的是"客户已被限制、订单还没冻"，而不是反过来——失败方向必须是安全的那一边。

## **决议五 · 报价的两种时效，锁的是两样东西**

|  | 有效期 | 锁住的是 | 过期意味着 |
|-|-|-|-|
| **兑换报价** | **30 秒** | 市场价 + 点差 + 服务费 | 价格会烂——这是兑换整条流程"不能等"的根因（决议六的来源） |
| **提现报价** | **300 秒（5 分钟）** | 手续费（不是汇率） | 重新取价即可，业务语义温和得多 |

两种报价单同一套四态生命周期（有效 → 已使用 / 已取消 / 已过期），都**一次性消费**：提交即作废，即使该笔随后被拒也不退还——客户不能拿同一个锁定价格反复试探合规。

## **决议六 · 能不能等，决定了裁决怎么被消费**

同一个 Sumsub 裁决落进三条流程，后果不同，根因是**这条流程能不能等**：

- **充值与提现能等。**"需要补充材料"→ 挂起等客户；"审核中"→ 挂起等 Sumsub，各自带自己的时钟。订单在那里等着不损失什么。
- **兑换不能等。**它是一个 30 秒的价格承诺。所以兑换把四种裁决**塌缩成两种**：干净 → 执行；其余一律拒单。要补的材料挂到**人**身上（不是单）——登记一张补料请求、不附带任何限制便签，客户补完料重新取一个当下的价格再下单。

一句话记住：**兑换死得便宜（只有出生锁一对挂账），代价是它必须死得快。**

## **决议七 · 对外识别与留痕的三条约定**

- **业务单号对外，UUID 不出门。**交易域单号家族：订单 `DEP` / `WDR` / `SWP`，资金单 `FDO`，报价 `WQT` / `SQT`，入金信号 `SIG`，限制便签 `RST`。格式统一为"前缀 + 日期六位 + 随机六位"。管理台不暴露内部 id。
- **旅程号全链继承。**一笔订单从建单到终局（含它引发的审批、资金单、补料）共享一个旅程标识；2026-09-16 起，六类详情页一键跳转审计链、按旅程一键回放全程。
- **三查成立：**按单号查、按客户查、按旅程查，三域都必须查得到——包括**被拒绝的动作**。"默默拦下"在这个系统里是禁止的。

**这张表里最值得记住的两条：**

- **边数 29 / 23 / 7 与"钱在谁手里"完全同序。**钱已经在手上、又不能拒收，就必须为它准备最多的出路（充值）；钱要出门，控制集中在出门前那一段（提现）；钱根本不出门，流程就可以简到七条边（兑换）——其中两条还是 2026-09-14 冻结翻案新开的处置弧。复杂度不是实现选择，是资金位置的必然结果。
- **充值与提现的"成功"都已经不是终点了。**对账域的补单流程各给它们加了一条边——入账后被退汇、出款后被退回。这两条边是**外部世界仍能反悔**的证据；兑换没有这条边，因为钱从未离开我方托管，外面没有人能把它退回来。

**⚠ 表中两处 ⚠ 的说明：**① 提现的"待合规 → 待签字"是一条**表外**状态变化，由建单后的异步路由直写，声明式迁移表里刻意没有这条边；② 提现的动作枚举里残留一个零引用死值（大额审批动作，随 10 态改造退役后未删声明）——2026-09-13 清死枚举只清了兑换侧，此值不影响任何行为，报表与代码阅读时视为历史遗留。两处均须在提现订单文档里如实标注。
